# Раздел 7 — Асинхронность

До сих пор шаги шли сразу: вызвал функцию — тело выполнилось (🔗 тема 11). Клик (🔗 тема 18) уже ломал эту картину: функцию вызывают **позже**. Этот раздел собирает «позже» в одну линию: таймер → Promise → удобный `await` → запрос в сеть → зачем `setTimeout(fn, 0)` печатает не сразу.

Event Loop — **последняя** тема раздела, не первая. Сначала научишься ждать результат, потом — почему порядок логов такой.

### Теория с аналогией

**Аналогия: «перезвоните через час»**

Ты не стоишь у двери весь час. Оставляешь номер (функцию) и занимаешься другим. Когда время вышло — тебе звонят. **Колбэк** — функция, которую вызовут потом, не сейчас.

Как мы видели в теме 18, `addEventListener("click", onGoClick)` уже колбэк: браузер позвонит по клику. `setTimeout` — тот же приём, только звонок по таймеру.

```javascript
console.log("А");

setTimeout(() => {
  console.log("Б");
}, 1000);

console.log("В");
```

Порядок: `А`, `В`, потом через ~секунду `Б`. Строка `setTimeout(...)` **не ждёт**. Она ставит будильник и идёт дальше. `1000` — миллисекунды.

`setTimeout(fn, 0)` — не «сейчас», а «как только освободишься после текущего кода». Это станет ясно в теме 24. Пока: ноль — всё равно очередь, не синхронный вызов.

**Колбэк — обычная функция**

```javascript
function later() {
  console.log("время");
}

setTimeout(later, 500);
// later без скобок: передаём функцию, не вызываем сейчас (тема 11)
```

`setTimeout(later(), 500)` — ошибка мысли: скобки вызовут `later` сразу, в таймер уйдёт её `return` (часто `undefined`).

**Событие = колбэк от среды**

```javascript
button.addEventListener("click", () => {
  console.log("клик — тоже потом, когда нажмут");
});
```

Таймер и клик — разные будильники, один навык: **отдал функцию, не вызвал**.

**Схема**

```
  сейчас:  console.log("А")
           setTimeout(колбэк, 1000)  →  среда заводит таймер
           console.log("В")
           (файл/обработчик закончились)

  потом:   среда вызывает колбэк → "Б"
```

`setInterval` повторяет; чтобы остановить — `clearInterval(id)`. Для учёбы хватает `setTimeout`. Id: `const id = setTimeout(...)`, `clearTimeout(id)` отменяет ещё не прозвеневший звонок.

---

### Где это в реальном коде

- Подсказка «сохранено» исчезает через 2 секунды: `setTimeout` чистит `textContent`.
- Кнопка — колбэк клика, без таймера.
- Отложить тяжёлую печать, чтобы сначала отрисовать «загрузка» — `setTimeout(fn, 0)` (грубо; тонкости — тема 24).
- Node: тот же `setTimeout`, без DOM.

---

### Паттерны

**1. В таймер — функция, не результат вызова**

Так лучше не делать: `setTimeout(later(), 1000)`.

Так лучше: `setTimeout(later, 1000)` или `setTimeout(() => later("ок"), 1000)`, если нужны аргументы.

Почему: скобки запускают сейчас. Таймер получает не функцию.

**2. Не путай «код ниже setTimeout» с «код после ожидания»**

Так лучше не делать: ждать, что `console.log` под `setTimeout` напечатается после колбэка.

Так лучше: всё «после ожидания» клади **внутрь** колбэка.

Почему: ниже по файлу — это «сразу», не «потом».

**3. Один колбэк — одна мысль**

Так лучше не делать: вложенные `setTimeout` в `setTimeout` в `setTimeout` («ад колбэков») для цепочки шагов.

Так лучше: для цепочки шагов дальше Promise / `await` (темы 21–22). Таймер — один отложенный жест.

Почему: вложенность невозможно читать. Это мотивация следующих тем, не запрет одного таймера.

---

### Вопросы

**Q1: Что такое колбэк простыми словами?**

Функция, которую ты отдаёшь другой функции или среде: «вызови это, когда событие / время / ответ». Ты не пишешь `later()` в момент готовности — пишешь `later` в момент подписки. Вызов сделает браузер или таймер.

**Q2: Почему «Б» печатается после «В», хотя `setTimeout` в файле раньше?**

Потому что `setTimeout` только ставит задачу. Пока текущий синхронный код (включая `"В"`) не закончится, колбэк не начнётся. Секунда — минимум ожидания, не «вырежи дыру в середине файла».

**Q3: Чем колбэк клика отличается от колбэка таймера?**

Тем, *кто* звонит: пользователь или часы. Форма одна: функция-значение. Клик может не случиться никогда; таймер почти наверняка прозвонит, если страницу не закрыли и не сделали `clearTimeout`.

**Q4: Зачем `clearTimeout`?**

Чтобы отменить ещё не сработавший будильник: человек ушёл с экрана, подсказка больше не нужна. Без отмены колбэк всё равно выстрелит и может тронуть уже несуществующий DOM.

**Q5: Можно ли вернуть из `setTimeout` значение в `const x` снаружи?**

Нет осмысленно: `setTimeout` возвращает id таймера, не результат колбэка. Результат «потом» живёт внутри колбэка или, в следующих темах, в Promise. Это та же ловушка, что ждать число от функции без `return` (тема 11), только ещё и время.

### Теория с аналогией

**Аналогия: талон в кафе**

Ты не стоишь у кофемашины. Берёшь талон (Promise): заказ **принят**, напитка ещё нет. Потом либо «готово» (успех), либо «закончилось молоко» (ошибка). `.then` — «когда готово, сделай это». `.catch` — «если сбой».

Как мы видели в теме 20, колбэк — один звонок. Promise — **объект-талон** (🔗 тема 14), у которого состояние и удобные методы вместо пирамиды вложений.

```javascript
const ticket = new Promise((resolve, reject) => {
  // эта функция запускается сразу
  const ok = true;
  if (ok) {
    resolve("латте");
  } else {
    reject(new Error("нет молока"));
  }
});

ticket
  .then((drink) => {
    console.log("получили:", drink);
  })
  .catch((error) => {
    console.log(error.message);
  });
```

- `resolve(value)` — успех, значение поедет в `.then`.
- `reject(error)` — сбой, в `.catch`. Обычно `Error` (🔗 тема 10).
- Пока ни `resolve`, ни `reject` — талон ждёт (pending).

**Цепочка**

```javascript
Promise.resolve(2)
  .then((n) => n + 1)
  .then((n) => {
    console.log(n); // 3
    return n * 10;
  })
  .then((n) => console.log(n)); // 30
```

`return` из `.then` становится входом следующего. Вернул Promise — следующий `.then` ждёт его. Забыл `return` — дальше `undefined`.

**Ошибка**

```javascript
Promise.reject(new Error("нет сети"))
  .then((data) => console.log(data))
  .catch((error) => console.log("сбой:", error.message));
```

`.catch` ловит reject и исключения внутри предыдущих `.then`. Без `.catch` будет «Unhandled Promise Rejection» в консоли.

Готовый успех для учёбы: `Promise.resolve(1)`. Готовый сбой: `Promise.reject(...)`.

**Схема**

```
  Promise
    pending  →  fulfilled (resolve)  →  .then(value)
             →  rejected  (reject)   →  .catch(error)
```

`setTimeout` + Promise — мост из темы 20:

```javascript
function wait(ms) {
  return new Promise((resolve) => {
    setTimeout(() => resolve("готово"), ms);
  });
}

wait(300).then((msg) => console.log(msg));
```

---

### Где это в реальном коде

- Ответ сети (тема 23): `fetch` уже возвращает Promise.
- «Подожди N мс» в тестах и анимациях — обёртка как `wait` выше.
- Чтение файла в Node (промис-API) — `.then` / `await`.
- Не оборачивай в `new Promise` то, что уже промис (`fetch`): лишняя коробка.

---

### Паттерны

**1. Всегда думай про сбой: `.catch` или `await` + `try`**

Так лучше не делать: голый `.then` и игнор консоли.

Так лучше: в конце цепочки `.catch((error) => ...)`.

Почему: ошибка сети иначе теряется или орёт Unhandled.

**2. Не клади синхронный код после `.then` и жди, что он «после»**

Так лучше не делать:

```javascript
ticket.then((x) => console.log("внутри", x));
console.log("снаружи"); // часто раньше «внутри»
```

Так лучше: продолжение — внутри `.then` или в теме 22 через `await`.

Почему: талон ещё не погашен, файл уже идёт дальше. Та же мораль, что у `setTimeout`.

**3. Один уровень `.then`, а не пирамида колбэков**

Так лучше не делать: `.then(() => { doMore((x) => { ... }) })` без нужды.

Так лучше: `return` промиса из `.then` и следующее `.then`.

Почему: цепочка плоская, как конвейер талонов.

---

### Вопросы

**Q1: Чем Promise отличается от колбэка?**

Колбэк — функция-звонок. Promise — объект «результат будет». На один талон можно повесить `.then` / `.catch`, передать талон в другую функцию, объединить позже. Колбэк не хранит успех сам по себе: кто не подписался вовремя, опоздал. У промиса состояние уже есть.

**Q2: Что принимают `resolve` и `reject`?**

`resolve` — значение успеха (строка, объект, число). `reject` — причина сбоя, лучше `Error` с `.message`. Не обязательно reject только строкой: тогда в `catch` придёт строка, без стека.

**Q3: Можно ли вызвать и `resolve`, и `reject`?**

Первый вызов фиксирует исход. Второй игнорируется. Талон не бывает «и латте, и ошибка». Не оставляй путь, где оба могут стрельнуть без `if`.

**Q4: Почему `console.log` сразу под `.then` печатается раньше?**

Потому что регистрация `.then` — синхронная, а колбэк `.then` — потом, когда талон погашен (даже если это `Promise.resolve`, чуть позже текущего кода — тема 24). «Потом» нельзя имитировать строкой ниже.

**Q5: Нужны ли сейчас `Promise.all` и `race`?**

Полезно знать, что они существуют: дождаться нескольких талонов сразу. Junior-база — один промис, `.then` / `.catch`. Несколько запросов параллельно — когда освоишь один `fetch`.

## Тема 22 — `async` / `await`

← Предыдущая тема: [21 — Promise](#тема-21--promise)  
→ Следующая тема: [23 — `fetch`](#тема-23--fetch)

---

### Теория с аналогией

**Аналогия: очередь у стойки, но без суеты**

`.then` — «запиши на стикере, что делать с кофе». `await` — «подожди у стойки, пока не дадут стакан, потом следующий шаг в том же рецепте». Ты всё ещё не блокируешь *весь браузер навечно как `sleep` в других языках*: функция `async` возвращает управление, пока ждёт. Но **в тексте** шаги выглядят последовательно.

Как мы видели в теме 11, у функции есть тело и `return`. `async function` всегда возвращает **Promise**. `return 5` → талон с пятёркой. `throw` → reject.

```javascript
async function main() {
  const ms = await wait(200);
  console.log("ждали " + ms);
  return "готово";
}

main().then((msg) => console.log(msg));
```

`await` можно писать **только внутри `async`**. Справа — промис (или значение, его обернут). Результат `await` — то, что было в `resolve`.

**Ошибки — снова `try` / `catch`**

```javascript
async function load() {
  try {
    const value = await Promise.reject(new Error("нет"));
    console.log(value);
  } catch (error) {
    console.log(error.message);
  }
}

load();
```

Это тот же `.catch`, только привычный блок из темы 10. Не оставляй `await` без обработки в учебном `main` — увидишь Unhandled.

**Не параллельность из воздуха**

```javascript
await first();
await second(); // second начнётся после first
```

Два независимых запроса «вместе» — запусти оба промиса, потом `await` каждого (или позже `Promise.all`). Два `await` подряд — очередь.

**Схема**

```
  async function f() {
    const a = await promiseA;  // пауза этой функции, не «заморозка файла навсегда»
    const b = await promiseB;
    return a + b;              // это resolve итогового промиса f()
  }
```

Стрелка: `const f = async () => { ... }`.

---

### Где это в реальном коде

- Почти весь современный `fetch` пишут в `async` обработчике кнопки или в `async function main`.
- Node-скрипт: `await` в `async main()` внизу файла `main()`.
- Нельзя `await` в самом верху обычного файла без `async` (классический скрипт). Модули (тема 25) в современных средах иногда позволяют top-level await — не база этого раздела.

---

### Паттерны

**1. `await` только в `async`**

Так лучше не делать: `const x = await fetch(...)` в середине обычной функции.

Так лучше: оберни в `async function` или сделай функцию `async`.

Почему: синтаксическая ошибка или путаница. Компилятор/движок не даст «подождать» вне async.

**2. Ошибки лови рядом с ожиданием**

Так лучше не делать: пять `await` подряд без `try`, один сбой роняет всё молча в консоль движка.

Так лучше: `try` вокруг логического куска (один сценарий загрузки).

Почему: пользователь видит твоё сообщение, не сырой Rejection.

**3. Не прячь `await` в цикле без мысли, если запросы независимы**

Так лучше не делать: `for` с `await fetch` на каждый id, когда можно спросить пачкой.

Так лучше: сначала пойми последовательный `await` (проще). Ускорение — когда база не путается.

Почему: Junior чаще ломает порядок, чем экономит миллисекунды. Сначала правильный смысл.

---

### Вопросы

**Q1: `await` замораживает всю страницу?**

Нет. Замирает выполнение **этой** async-функции до resolve/reject. Другие колбэки (клик, другой таймер) могут работать. Это не `while` на миллион итераций, который реально держит вкладку. Тема 24 уточнит, кто кого вставляет в очередь.

**Q2: Что возвращает `async function` без `await`?**

Всё равно Promise. `async function f() { return 1; }` → промис с `1`. Вызов `f()` сразу не даёт `1` в `const x = f()`, даёт талон. Нужна единица — `await f()` или `.then`.

**Q3: Чем `try` / `catch` вокруг `await` лучше `.catch`?**

Не лучше универсально — то же самое. Удобнее, когда шагов много: обычный `if` и несколько `await` в одном блоке. Короткий один промис часто читается и цепочкой `.then`. Выбери читаемость.

**Q4: Можно ли `await` не промис?**

Да: `await 5` даст `5`. Движок обернёт значение. Имеет смысл ждать то, что реально асинхронно. Не украшай каждое число `await` ради стиля.

**Q5: Почему после `const p = wait(1000)` без `await` код ниже бежит сразу?**

Ты получил талон, не содержимое. Без `await` / `.then` ожидания нет. Частая опечатка: забыли `await` и думают, что в `p` уже строка `"готово"`. Проверь: `typeof` / лог покажет Promise.

```javascript
// до → снаружи → (пауза) → после
```

**Инсайт:** `await` ставит паузу внутри `async`, не ниже по файлу. Снаружи вызов `run()` не ждёт, пока ты сам не `await run()`.

## Тема 23 — `fetch`

← Предыдущая тема: [22 — `async` / `await`](#тема-22--async--await)  
→ Следующая тема: [24 — Event Loop упрощённо](#тема-24--event-loop-упрощённо)

---

### Теория с аналогией

**Аналогия: письмо на почту**

`fetch(url)` — отдал письмо, получил талон (Promise). Когда ответ пришёл — это ещё конверт: статус, заголовки. Тело (JSON, текст) читают **вторым** ожиданием: `response.json()` тоже промис.

Как мы видели в темах 21–22, без `await` / `.then` в переменной будет талон, не данные. Как в теме 10, кривой JSON — исключение на `json()`. Как в теме 8, статус `404` — не всегда throw: `fetch` по умолчанию **успешный промис** даже на 404. Проверяй `response.ok`.

```javascript
async function loadTodo() {
  try {
    const response = await fetch("https://jsonplaceholder.typicode.com/todos/1");

    if (response.ok === false) {
      throw new Error("HTTP " + response.status);
    }

    const data = await response.json();
    console.log(data.title);
  } catch (error) {
    console.log(error.message);
  }
}

loadTodo();
```

`response.ok` — булево, статус 200–299. Иначе сам `throw` — попадёшь в `catch`.

Тело один раз: второй `response.json()` не прочитать. Нужны и текст, и объект — сначала реши формат.

В браузере чужой сайт может отказать из‑за CORS. Учебный JSONPlaceholder обычно доступен. Если консоль про CORS — это политика браузера, не «ты неправильно написал await». Node 18+ тоже имеет `fetch`.

**Схема**

```
  fetch(url)
    → Promise<Response>     конверт (ok, status)
    → response.json()
    → Promise<объект>       тело
```

POST позже: `fetch(url, { method: "POST", headers, body })`. Junior-база — GET и JSON.

---

### Где это в реальном коде

- Подгрузить заголовок новости в `#out` (темы 17–18): `await fetch` в обработчике, `textContent = data.title`.
- Проверка «сервер жив»: смотри `ok`, не только наличие JSON.
- Форма (тема 19): после `preventDefault` отправить поля — следующий шаг после GET.

---

### Паттерны

**1. Два ожидания: ответ, потом тело**

Так лучше не делать: `const data = await fetch(url)` и ждать объект с полями.

Так лучше: `const response = await fetch(url)` → проверка `ok` → `const data = await response.json()`.

Почему: первая пауза — сеть и заголовки. Данные — вторая.

**2. HTTP-ошибка — твоя проверка**

Так лучше не делать: считать, что `catch` поймает 404.

Так лучше: `if (response.ok === false) throw new Error(...)`.

Почему: спецификация `fetch`: сеть упала → reject; 404 → fulfilled с `ok === false`.

**3. На страницу — `textContent`, в консоль — отладка**

Так лучше не делать: `innerHTML = data.title` с сервера без доверия.

Так лучше: как в теме 17, `textContent`.

Почему: XSS. Сервер тоже может прислать сюрприз.

---

### Вопросы

**Q1: Почему после `fetch` ещё `json()`?**

`fetch` даёт описание ответа. Тело может быть картинкой, HTML, JSON. `json()` — «прочитай тело как JSON» и тоже асинхронно (парсинг/поток). Два этапа — две паузы.

**Q2: `catch` поймает 500?**

Нет, если соединение удалось. Поймает обрыв сети, CORS в виде TypeError, сбой `json()`. Статус 500 — смотри `ok` и `status`. Имеет смысл объединить: не ok → `throw`, тогда один `catch` на оба мира.

**Q3: Можно ли `fetch` в Node?**

В современных Node — да, глобальный `fetch`. В старых — нет или нужен пакет. Для курса: браузер + относительно новый Node. Нет `fetch` — обнови Node или гоняй пример в браузере.

**Q4: Что такое CORS в двух предложениях?**

Браузер не даёт странице с одного сайта читать ответ другого, если тот не разрешил. Это защита пользователя, не ошибка твоего `await`. Учебные API с разрешением работают; свой бэкенд на другом порту без заголовков — увидишь CORS в Console.

**Q5: Куда деть `loadTodo` — в клик или сразу при загрузке?**

Оба варианта. Сразу — вызов `loadTodo()` внизу скрипта. По кнопке — `addEventListener` и `async` обработчик: `go.addEventListener("click", () => { loadTodo(); })` или `async () => { await loadTodo(); }`. Не забудь `preventDefault`, если это submit.

---

### Практическое задание

Браузер: `fetch.html` + `fetch.js`, абзац `#out`. Либо только `fetch.js` в Node 18+.

1. `async function load()` с `fetch` на `https://jsonplaceholder.typicode.com/todos/1`.
2. Если не `ok` — сообщение в `#out` или `console.log`.
3. Иначе выведи `data.title` (на странице — `textContent`).
4. Обёрни в `try` / `catch`.
5. Вызови `load()`.

Нет сети — в `catch` должно быть понятно, что сбой, не пустая страница без лога.

---

### Решение с инсайтом

```javascript
async function load() {
  const out = document.querySelector("#out");

  try {
    const response = await fetch(
      "https://jsonplaceholder.typicode.com/todos/1"
    );

    if (response.ok === false) {
      throw new Error("HTTP " + response.status);
    }

    const data = await response.json();

    if (out !== null) {
      out.textContent = data.title;
    } else {
      console.log(data.title);
    }
  } catch (error) {
    const message = error.message;
    if (out !== null) {
      out.textContent = message;
    }
    console.log(message);
  }
}

load();
```

В чистом Node убери DOM, оставь `console.log`.

**Инсайт:** `fetch` — два промиса (конверт и тело) и отдельная проверка `ok`. Сеть — не `if`, это `await` плюс явные сбои.

## Тема 24 — Event Loop упрощённо

← Предыдущая тема: [23 — `fetch`](#тема-23--fetch)  
→ Следующая тема: [25 — `import` / `export`](section_8_modules.md#тема-25--import--export)

---

### Теория с аналогией

**Аналогия: один повар и окошко выдачи**

JavaScript в среде (браузер / Node) готовит **одно блюдо за раз** — текущий стек вызовов. Таймер и сеть готовятся «на кухне сзади» (среда). Когда повар свободен, он берёт следующее из окошка выдачи.

Как мы видели в темах 20–22, колбэк и `.then` не вклиниваются *внутрь* текущего синхронного кода. Event Loop — имя этой дисциплины: «доделай текущее, потом возьми из очереди».

Упрощённо две ленты выдачи:

1. **Сначала** мелкие «сразу после текущего кода» задачи от промисов (`then` / очередь микрозадач).
2. **Потом** макрозадачи: колбэк `setTimeout`, часто клик как отдельный заход.

Поэтому классика:

```javascript
console.log("1");

setTimeout(() => console.log("2"), 0);

Promise.resolve().then(() => console.log("3"));

console.log("4");
```

Порядок: `1`, `4`, `3`, `2`.

- `1` и `4` — синхронно, пока повар у плиты.
- `3` — промис уже выполнен, `.then` встаёт в микроочередь, её разбирают **до** таймера.
- `2` — таймер с нулём: «когда освободишься и микрозадачи пусты».

Не зубрить все виды очередей как на middle. Запомнить:

```
  1. Весь текущий синхронный код
  2. Все .then / очередь промисов (пока не кончатся)
  3. Один (или следующий) таймер / похожая макрозадача
  4. Повтор с пункта 2
```

`await` после промиса продолжает функцию как микрозадачу — поэтому `"после"` из темы 22 идёт не между `"до"` и `"снаружи"`, а когда талон погас.

**Схема**

```
  [синхронный код] ──► стек пуст
                           │
                           ▼
                    очередь .then
                           │
                           ▼
                    setTimeout / клик
```

Клик (тема 18) — тоже «потом, когда стек свободен». Не одновременно с бесконечным `while` — зависший синхронный цикл не даст обработать клик. Не пиши пустой `while (true)`.

---

### Где это в реальном коде

- «Почему лог после `fetch` раньше данных?» — данные в `await`/`.then`, не ниже.
- «Почему UI не жмёт, пока крутится длинный `for`?» — повар занят, клик в очереди.
- Отладка порядка: нарисуй три корзины: сейчас / промисы / таймеры.

---

### Паттерны

**1. Предсказывай лог: сначала синхрон, потом промис, потом timeout(0)**

Так лучше не делать: ставить `setTimeout(fn, 0)` и ждать, что он обгонит `Promise.resolve().then`.

Так лучше: помнить пример `1 4 3 2`.

Почему: ноль на таймере — не высший приоритет.

**2. Длинный синхронный цикл — враг кликов**

Так лучше не делать: считать миллионы итераций в обработчике без пауз.

Так лучше: режь работу или уноси в `await`/таймер кусками, когда понадобится. На старте — просто не блокируй.

Почему: Event Loop не прерывает текущую функцию посередине ради клика.

**3. Не учи наизусть MutationObserver и queueMicrotask**

Так лучше не делать: коллекция очередей как у middle-интервью.

Так лучше: три факта выше. Остальное — когда реально встретишь API.

Почему: Junior ломается на порядке логов, не на названиях очередей.

---

### Вопросы

**Q1: Почему `setTimeout(fn, 0)` не означает «сейчас»?**

Ноль — «поставь в очередь таймеров». Текущий код и микрозадачи промисов идут раньше. Ноль гарантирует лишь «не раньше, чем стек опустеет», не «перед всем».

**Q2: Почему `.then` у уже resolved промиса всё равно «позже»?**

Колбэк `.then` не вызывается синхронно в той же пачке, что `Promise.resolve()`. Его кладут в микроочередь. Поэтому `"сразу"` под цепочкой печатается раньше `.then`, даже без `setTimeout`.

**Q3: Клик может прервать выполняющуюся функцию?**

Нет. Сначала функция доработает (или упрётся в `await`). Потом loop возьмёт событие. Зависший синхронный код = мёртвая кнопка, пока не закончится.

**Q4: `await fetch` крутит Event Loop или стопорит его?**

Пока ждёшь сеть, стек этой async-функции свободен для *других* задач: клики, таймеры. Когда ответ пришёл, продолжение `await` встаёт в очередь (как микрозадача). Страница может оставаться живой — в этом смысл асинхронности.

**Q5: Нужно ли это на каждом собеседовании Junior?**

Часто спросят порядок трёх `console.log` с timeout и промисом. Ответ из этой темы достаточен. Полный VIP-банк micro vs macro — курс middle, тема Event Loop там с другой глубины.

