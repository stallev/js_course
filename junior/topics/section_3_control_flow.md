# Раздел 3 — Управление потоком

До сих пор код шёл сверху вниз, как рецепт без развилок (🔗 темы 1–3). Типы и `===` (🔗 темы 4–7) дали вопрос «это то или нет». Этот раздел отвечает, **что делать с ответом**: выбрать ветку, повторить шаг, не дать скрипту упасть молча.

Без функций и DOM: решения печатаем в консоль. Ветвление понадобится кнопкам и формам позже (🔗 темы 17–19).

## Тема 8 — `if` / `else` / `switch`

← Предыдущая тема: [7 — `null` и `undefined`](section_2_types.md#тема-7--null-и-undefined)  
→ Следующая тема: [9 — Циклы](#тема-9--циклы)

---

### Теория с аналогией

**Аналогия: развилка на тропинке**

Идёшь по лесу. Табличка: «если дождь — навес, иначе — поляна». Код тоже выбирает **одну** тропу и не ходит по обеим сразу.

Как мы видели в 🔗 теме 6, сравнение `===` даёт булево. `if` берёт это булево (или значение, которое ведёт себя как да/нет) и решает, выполнять ли блок в фигурных скобках.

`if` — **инструкция** (🔗 тема 3), не выражение: её нельзя положить справа от `=` как число. Это приказ «если правда — сделай шаги».

```javascript
const age = 20;

if (age >= 18) {
  console.log("можно");
} else {
  console.log("ещё рано");
}
```

Скобки после `if` — условие. Фигурные `{ }` — тело ветки. Даже для одной строки в этом курсе **ставь скобки**: так не потеряешь вторую строку, которую добавишь завтра.

**`else if` — ещё одна табличка**

```javascript
const score = 75;

if (score >= 90) {
  console.log("отлично");
} else if (score >= 60) {
  console.log("зачёт");
} else {
  console.log("пересдача");
}
```

Проверяются сверху вниз. Сработала первая правда — остальные `else if` не смотрят. Поэтому порядок важен: сначала узкое условие (`>= 90`), потом широкое (`>= 60`).

**Что считается «правдой» без явного `true`**

В скобках `if` значение приводится к да/нет:

```
ложно (не зайдём в if):   false, 0, "", null, undefined, NaN
правдиво (зайдём):        true, любые другие числа, непустые строки, объекты
```

```javascript
const name = "";

if (name) {
  console.log("есть имя");
} else {
  console.log("имя пустое");
}
```

Это удобно и опасно: `if (age)` не зайдёт при `age === 0`. Для возраста и счётчиков пиши явно: `if (age >= 18)`, `if (count === 0)`. Для «строка не пустая» `if (name)` нормален, если ты помнишь, что `""` — ложь.

**Логические «и» / «или» / «не»**

```javascript
const age = 20;
const hasTicket = true;

if (age >= 18 && hasTicket) {
  console.log("вход");
}

if (age < 14 || age > 65) {
  console.log("льготный");
}

if (!hasTicket) {
  console.log("нет билета");
}
```

- `&&` — оба условия правда.
- `||` — достаточно одного.
- `!` — перевернуть булево (🔗 тема 5).

Сравнивай через `===`, как в теме 6: `if (status === "ok")`, не `if (status == "ok")`.

**`switch` — несколько табличек на одно значение**

Когда ветки — это «статус равен вот этой строке, или вот той»:

```javascript
const status = "ok";

switch (status) {
  case "ok":
    console.log("успех");
    break;
  case "pending":
    console.log("ждём");
    break;
  default:
    console.log("неизвестно");
}
```

`break` обязателен, пока учишься: без него выполнение **провалится** в следующий `case`. `default` — «ни один не совпал». Сравнение в `switch` — строгое, как `===`.

Для диапазонов (`age >= 18`) `if` яснее, чем `switch`.

**Схема**

```
  условие?
      │ да                    │ нет
      ▼                       ▼
   блок if                 else / конец

  else if — следующая табличка, только если предыдущие солгали
```

---

### Где это в реальном коде

- Скрипт в Node: если не передали аргумент (`=== undefined`) — печать подсказки и выход, иначе расчёт.
- Ответ сервера: `if (status === "ok")` показать данные, `else` — сообщение об ошибке (пока в консоль).
- Кнопка (🔗 тема 18): если поле пустое — не отправлять форму.
- Режим: `switch (command)` для `"start"` / `"stop"` / `"help"` в маленьком CLI.

---

### Паттерны

**1. Явное сравнение для чисел и статусов**

Так лучше не делать: `if (count)` и считать, что ноль обработается отдельно «как-нибудь».

Так лучше: `if (count === 0)` и `if (count > 0)`.

Почему: ноль — валидное количество (🔗 тема 7). В `if (count)` он выглядит как «нет значения».

**2. Всегда фигурные скобки**

Так лучше не делать: `if (ready) console.log("ок");` без `{ }`.

Так лучше: блок в скобках, даже из одной строки.

Почему: добавишь вторую строку — без скобок она выполнится всегда, и баг не виден глазом.

**3. `switch` — только равные варианты, и с `break`**

Так лучше не делать: `switch` по возрасту с десятью `case` и забытым `break`.

Так лучше: диапазоны — `if` / `else if`. Список точных строк — `switch` и `break` в каждой ветке.

Почему: провал без `break` печатает два сообщения подряд и выглядит как «магия».

---

### Вопросы

**Q1: Чем `if` отличается от выражения?**

`if` — инструкция: приказ выбрать ветку. У него нет значения, которое кладут в `const`. Справа от `=` по-прежнему выражение: сравнение `age >= 18` или вызов, который вернёт булево. Путать их — та же ошибка, что `console.log(let x = 1)` в теме 3.

**Q2: В каком порядке проверяются `else if`?**

Сверху вниз, до первой правды. Дальше остальные не выполняются. Если широкое условие поставить первым (`score >= 60` раньше `>= 90`), до «отлично» никогда не дойдёшь: 95 уже «зачёт». Сначала более узкий случай.

**Q3: Почему `if (name)` срабатывает на любую непустую строку?**

Непустое считается правдивым, `""` — ложным. Это сокращение для «есть текст». Не используй тот же приём для чисел, если `0` имеет смысл. Для `null` и `undefined` `if (value)` тоже не зайдёт — иногда это то, что нужно, иногда лучше `value === null`.

**Q4: Зачем `break` в `switch`?**

Без него код не выходит из `switch`, а идёт в следующий `case`. Написали `"ok"` — выполнится и `"ok"`, и `"pending"`, если забыли `break`. Пока учишься, ставь `break` всегда. Сознательный «провал» — редкий приём, не база.

**Q5: Когда брать `switch` вместо `if`?**

Когда одно значение сравнивается с несколькими точными вариантами: статус, команда, код ответа. Когда условия разные (`age >= 18` и `hasTicket === true`) — `if`. Не переписывай всё в `switch` ради «красоты».

## Тема 9 — Циклы

← Предыдущая тема: [8 — `if` / `else` / `switch`](#тема-8--if--else--switch)  
→ Следующая тема: [10 — `try` / `catch`](#тема-10--try--catch)

### Теория с аналогией

**Аналогия: конвейер**

Один и тот же жест — «положи наклейку» — для каждой банки. Цикл: *пока есть банки* (или *ровно N раз*) делай тело. Без цикла ты скопируешь `console.log` пять раз и ошибёшься на шестой.

Как мы видели в 🔗 теме 8, тело в `{ }` — набор инструкций. Цикл оборачивает это тело и решает, зайти ли ещё раз. Счётчик — обычный `let` (🔗 тема 2): его **меняют**, поэтому не `const`.

**`for` — «повтори известное число раз»**

```javascript
for (let i = 1; i <= 5; i = i + 1) {
  console.log(i);
}
// 1 2 3 4 5  (каждый на своей строке)
```

Три части в скобках:

```
  for (старт;  пока правда — крутить;  шаг после круга)
         │           │                      │
      let i = 1    i <= 5               i = i + 1
```

`i` — индекс, привычное имя счётчика. Можно `i += 1` или `i++` — пока достаточно `i = i + 1`, чтобы видеть присваивание.

**`while` — «пока условие живо»**

```javascript
let n = 3;

while (n > 0) {
  console.log(n);
  n = n - 1;
}
```

Условие проверяется **перед** кругом. Если сразу ложь — тело ни разу. Забудь изменить `n` — цикл бесконечный: консоль повиснет. Тогда останови выполнение в терминале (`Ctrl+C`).

**`for...of` — «для каждого элемента списка»**

Строка и массив — последовательности. Массивы подробно — 🔗 тема 15; сейчас достаточно литерала:

```javascript
const word = "JS";

for (const letter of word) {
  console.log(letter);
}
// "J" затем "S"

const nums = [10, 20, 30];

for (const value of nums) {
  console.log(value);
}
```

В `for...of` элемент можно брать `const`: ты не переназначаешь `letter`, движок сам кладёт следующее. Это не `for (const i = 0; ...)` — там счётчик меняется, нужен `let`.

Цикл `for...in` (по ключам объекта) в Junior **не используй** для массивов: легко поймать лишнее. Объекты — тема 14.

**`break` и `continue`**

```javascript
for (let i = 1; i <= 10; i = i + 1) {
  if (i === 3) {
    continue; // пропусти этот круг
  }
  if (i === 5) {
    break;    // выйди из цикла совсем
  }
  console.log(i);
}
// 1 2 4
```

`continue` — «к следующему кругу». `break` — «конвейер стоп». Внутри `if`, как в теме 8.

**Схема**

```
  for / while:
    условие правда? --нет--> конец
         │ да
         ▼
       тело
         │
         └── снова проверить условие
```

---

### Где это в реальном коде

- Печать таблицы: `for` от 1 до 10, строка `` `${i} * 2 = ${i * 2}` `` (🔗 тема 5).
- Разбор текста: `for...of` по символам, считаешь пробелы.
- Список имён (когда будут массивы): одно сообщение на элемент, не копипаста `console.log`.
- «Пока файл не кончился» в Node — часто `while`; на старте хватит `for` с известной длиной.

---

### Паттерны

**1. Шаг внутри `while` не забывай**

Так лучше не делать: `while (n > 0) { console.log(n); }` без `n = n - 1`.

Так лучше: в теле меняй то, от чего зависит условие, или бери `for`, если число кругов известно.

Почему: бесконечный цикл выглядит как «терминал завис», хотя завис твой код.

**2. Известный диапазон — `for`, перебор значений — `for...of`**

Так лучше не делать: руками `i` и `word[i]`, если нужно только «каждая буква».

Так лучше: `for (const letter of word)`.

Почему: меньше шанс выйти за край строки. Индекс оставь, когда номер позиции сам нужен.

**3. Не копируй тело цикла пять раз вместо цикла**

Так лучше не делать: пять одинаковых `console.log` с разными числами.

Так лучше: один `for`.

Почему: правило «как считать» живёт в одном месте. Меняешь формулу — меняешь одну строку.

---

### Вопросы

**Q1: Чем `for` отличается от `while`?**

Оба крутят тело, пока условие правда. В `for` старт, условие и шаг собраны в скобках — удобно, когда знаешь «от и до». `while` оставляет шаг тебе в теле — удобно, когда стоп зависит от данных, не от счётчика. Можно написать одно через другое; бери тот, который читается вслух проще.

**Q2: Почему счётчик в `for` — `let`, а буква в `for...of` — `const`?**

Счётчик каждый круг *переназначают* (`i = i + 1`) — нужен `let`. В `for...of` имя `letter` на круге не присваиваешь сам, подставляется следующее значение — `const` уместен. Это те же правила темы 2.

**Q3: Что будет, если условие `while` сразу ложно?**

Тело не выполнится ни разу. Это нормально, не ошибка. `for` с `i = 0; i < 0` ведёт себя так же. Если ждал хотя бы один круг — проверь стартовые значения.

**Q4: Чем `break` отличается от `continue`?**

`continue` пропускает остаток *этого* круга и идёт к следующему. `break` выходит из цикла полностью. Оба — инструкции внутри тела, обычно рядом с `if`.

**Q5: Нужно ли сейчас учить `for...in` и `do...while`?**

`for...in` для массивов вреден как привычка — отложи до объектов и то осторожно. `do...while` крутит тело *сначала*, потом проверяет условие — редкость. База Junior: `for`, `while`, `for...of`.

## Тема 10 — `try` / `catch`

### Теория с аналогией

**Аналогия: хрупкая ваза и поддон**

Обычный код без `try`: ваза упала — осколки по всей кухне, дальше рецепт не готовится. `try` / `catch` — поддон: падение **замечают**, подметают, можно написать «не получилось» и идти дальше.

Как мы видели в 🔗 теме 8, `if` ловит *ожидаемые* развилки: возраст мал, статус не `"ok"`. `try` / `catch` — для **сбоев**, которые прерывают выполнение: синтаксис уже прошёл, а в рантайме «так нельзя».

Пока без иерархии классов ошибок и без `async`. Бытовой уровень: обернул опасное, поймал, прочитал сообщение.

```javascript
try {
  const data = JSON.parse("{ не json }");
  console.log(data);
} catch (error) {
  console.log("не разобрали JSON");
  console.log(error.message);
}

console.log("скрипт жив");
```

`JSON.parse` ждёт строку формата JSON. Кривой текст — исключение, без `try` Node/браузер остановит файл. С `catch` ты решаешь, что сказать, и выполнение продолжается.

**Схема**

```
  try { опасные шаги }
      │
      ├── всё ок  →  catch пропускаем, дальше обычный код
      └── сбой    →  прыжок в catch (error)
                         │
                         └── сообщение, запасной путь, скрипт не умер
```

**Своя ошибка: `throw`**

Иногда сбой — твоё правило, не встроенная функция:

```javascript
const raw = "привет";
const age = Number(raw);

try {
  if (Number.isNaN(age)) {
    throw new Error("возраст не число");
  }
  console.log(age);
} catch (error) {
  console.log(error.message);
}
```

`throw` — бросить. `new Error("...")` — объект с полем `.message`. В `catch` имя `error` — обычная коробка (как параметр; функции — тема 11).

**`finally` — коротко**

```javascript
try {
  console.log("работа");
} catch (error) {
  console.log(error.message);
} finally {
  console.log("закрыли ресурс / всегда");
}
```

Блок `finally` выполняется и при успехе, и при ошибке. Нужен, когда «убрать за собой» надо в любом случае. На старте чаще хватает `try` / `catch`.

**Чего `try` не заменяет**

Пустой `catch` — поддон без веника: ошибка съедена, отладка невозможна. Не оборачивай весь файл в один `try`. `if` для `age < 18` — не исключение, а ветка.

---

### Где это в реальном коде

- Разбор JSON из файла или ответа сети (позже `fetch`, 🔗 тема 23): `JSON.parse` в `try`.
- `Number(raw)` плюс своё правило: не число — `throw`, пользователь видит понятный текст в консоли.
- Браузер: иногда падает чужой кусок; свой `catch` хотя бы пишет причину в Console (🔗 тема 1).
- Не ставь `try` вокруг каждого `console.log` — только там, где сбой реален и понятен.

---

### Паттерны

**1. Лови то, что умеешь объяснить**

Так лучше не делать: пустой `catch (e) {}`.

Так лучше: `console.log(error.message)` или свой текст плюс сообщение.

Почему: молчаливый `catch` превращает баг в «ничего не произошло» — хуже, чем падение в теме 1, где консоль кричит.

**2. Ожидаемая развилка — `if`, сбой — `throw` / `catch`**

Так лучше не делать: `throw` вместо `else` для «возраст меньше 18» в учебном скрипте приветствия.

Так лучше: `if (age < 18) { console.log("рано"); }`. `throw` — когда продолжать бессмысленно: вход не число, JSON битый.

Почему: исключение — редкий сбой, не вторая форма `if`. Путаница потом мешает читать чужой код.

**3. Узкий `try`**

Так лучше не делать: весь скрипт в одном `try`, в `catch` одно «ошибка».

Так лучше: оберни `JSON.parse` или проверку входа, остальное оставь падать как обычно.

Почему: увидишь *какая* операция сломалась. Широкий `try` прячет строку с багом.

### Вопросы

**Q1: Чем `try` / `catch` отличается от `if` / `else`?**

`if` выбирает ветку по значению, которое ты сам проверил. `catch` срабатывает, когда шаг *бросил исключение*: движок не может продолжить эту операцию. Не всякая «ложь» — ошибка. Статус `"error"` от сервера часто обрабатывают `if (status === "error")`, а кривой JSON — `catch`.

**Q2: Что лежит в `error` внутри `catch`?**

Объект ошибки. Для учёбы главное поле — `error.message`, человекочитаемая строка. `console.log(error)` напечатает больше (стек вызовов) — полезно при отладке, как консоль в теме 1. Не обязательно разбирать все поля.

**Q3: Продолжится ли код после `catch`?**

Да, если не бросил снова. Строки ниже `try` / `catch` выполнятся. Без `try` исключение останавливает файл. В этом смысл поддона: кухня не закрывается.

**Q4: Когда писать `throw new Error(...)` самому?**

Когда вход нарушает *твоё* правило, а встроенная функция молчит или даёт `NaN`. Пример: после `Number` проверка `Number.isNaN` и явный бросок с понятным текстом. Не бросай «на всякий случай» в каждой функции — сначала `if`.

**Q5: Нужны ли сейчас свои классы вроде `ValidationError`?**

Нет. Junior-уровень: `Error` и `.message`. Иерархия ошибок — глубина middle. Не усложняй учебный файл наследованием.

### Практическое задание

Файл `safe-parse.js`.

1. Константа `const raw = "{ не json }"`.
2. В `try` вызови `JSON.parse(raw)` и выведи результат.
3. В `catch` выведи `"не JSON"` и `error.message`.
4. После блока выведи `"готово"` — строка должна появиться даже при ошибке.
5. Вторым экспериментом поставь `raw` в `'{"ok": true}'` и убедись, что `catch` не срабатывает, а `"готово"` остаётся.

### Решение с инсайтом

```javascript
const raw = "{ не json }";

try {
  const data = JSON.parse(raw);
  console.log(data);
} catch (error) {
  console.log("не JSON");
  console.log(error.message);
}

console.log("готово");
```

**Инсайт:** `try` / `catch` — не способ спрятать баг, а способ *пережить* ожидаемый сбой и объяснить его. Пустой `catch` хуже падения: ты ничего не узнаешь.
