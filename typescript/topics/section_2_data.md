## Тема 3 — Примитивы и вывод типов

← Предыдущая тема: [2 — Запуск](section_1_setup.md#тема-2--запуск-tsx-tsc-tsconfig)  
→ Следующая тема: [4 — Объекты, массивы, кортежи, `type`](#тема-4--объекты-массивы-кортежи-type)

### Теория с аналогией

**Аналогия: ценник на полке и ценник «и так видно»**

`let age: number = 18` — ценник написан. `let age = 18` — продавец (компилятор) сам видит, что это число. Это **вывод типов** (inference).

```typescript
let title = "Курс"; // string
let year = 2026;    // number
let ready = true;   // boolean

title = "Junior";
// title = 1; // ошибка: number не string
```

Как в 🔗 Junior теме 2, `const` нельзя переприсвоить. У `const n = 1` тип часто **литерал** `1`, не просто `number`: значение не сменится, компилятор это учитывает. У `let n = 1` тип шире — `number`, потому что потом могут присвоить `2`.

**Когда аннотация нужна сразу**

- параметры функций (тема 7) — снаружи не из чего вывести;
- пустой массив: `const ids: number[] = []` иначе станет `never[]` и туда ничего не положишь.

`bigint` и `symbol` в Junior почти не нужны — и здесь не ядро. Повседневный слой: `string`, `number`, `boolean`.

### Где это в реальном коде

Счётчик кликов — `number`. Текст кнопки — `string`. Флаг «форма валидна» — `boolean`. Как Junior темы 5 и 18, только с подписью на границе функции.

### Паттерны

❌ `let x: string | number | boolean | null` «на всякий случай»  
✅ Один смысл — один тип; несколько смыслов — тема 5, осознанно  
Почему: широкий тип ничего не ловит.

❌ `let n: number = 1` везде  
✅ `let n = 1`, аннотация на параметре  
Почему: вывод уже знает.

❌ Менять тип той же переменной (`let x = 1; x = "a"`)  
✅ Две переменные или union, если правда оба варианта  
Почему: в JS так можно, в strict TS — нет, и это плюс.

### Вопросы

**Q1: Откуда TypeScript знает тип `let n = 1`?**  
Из литерала `1` в правой части. Компилятор выводит `number` для `let`, потому что переменную ещё можно сменить на другое число. Это не runtime-`typeof` из Junior: ярлык появляется до запуска. Если присвоить строку, `tsc` станет красным.

**Q2: Чем аннотация `: number` отличается от `typeof` в Junior теме 4?**  
`typeof` смотрит на уже лежащее значение, когда программа работает. Аннотация — обещание для компилятора, после стирания (тема 1) в JS её нет. Можно обойти проверку и получить другой runtime-тип. Для слоя правило: не обходи, чини форму.

**Q3: Почему пустой `const xs = []` неудобен?**  
Вывод не видит элементов и часто даёт `never[]`: «массив, куда нельзя положить ничего осмысленного». Напиши `number[]` или положи первый элемент, чтобы вывести тип. Пустой массив в JS законен, в TS без подсказки — ловушка.

**Q4: Есть ли тип у `const`, если значение нельзя сменить?**  
Да. `const` запрещает новое присваивание имени, но тип всё равно проверяют при *использовании*: передал `n` в функцию, ждущую строку — ошибка. Часто тип уже литерал. Это не «тип не нужен», это «переприсвоить нельзя, проверить всё равно можно».

**Q5: Нужно ли писать `: boolean` для `const ready = true`?**  
Нет, если вывод очевиден. Аннотация шумная и не ловит лишнего. Исключение — публичная граница: возвращаемое значение функции, поле объекта, параметр. Внутри `describePrimitives` хватает вывода.

**Q6: Чем вывод у `let n = 1` отличается от `const n = 1`?**  
`let` готов к другим числам → обычно `number`. `const` фиксирует `1` → литеральный тип `1`. Это заметно, когда функция ждёт именно `1` или union `"on" | "off"`. Пока не тема 5, достаточно: `const` уже, `let` шире.

**Q7: Где аннотация обязательна — у локальной константы или у параметра?**  
У параметра: вызывающий снаружи, компилятор не видит, что ему передадут. Локальная `const title = "Курс"` выводится. Пустой массив и «хочу именно `string | null`» — тоже место для явного типа.

**Q8: Почему в этом слое нет отдельной темы про `bigint` и `symbol`?**  
Как в Junior: они существуют, в повседневном коде моста почти не встречаются. Ядро — строка, число, булево, плюс объекты дальше. Не строй примеры курса на `10n`, пока не понадобится счётчик за пределами `number`.

**Q9: Можно ли в strict TS сделать `let x = 1; x = "a"`?**  
Нет. В JS так делают, и это источник багов «думал, что число». TS фиксирует тип после первого вывода. Если правда нужны оба вида — тема 5, union, осознанно. Иначе два имени.

**Q10: Что TypeScript не выводит «из головы», если значения ещё нет?**  
Параметры, пустые коллекции, данные с сети (тема 13). Вывод работает от литералов и от уже типизированных вызовов. Нет литерала — нет догадки, нужна аннотация или сужение (тема 8).

### Практическое задание

В `sandbox/js_sandbox/topics/topic_3/exercises.ts`: функция `describePrimitives` — залогируй строку, число и boolean; верни длину строки как `number`.

### Решение с инсайтом

```typescript
export function describePrimitives(): number {
  const title = "Курс";
  const year = 2026;
  const ready = true;
  console.log(title, year, ready);
  return title.length;
}
```

**Инсайт:** локальным значениям часто хватает вывода; контракт — на входе и выходе функции.

## Тема 4 — Объекты, массивы, кортежи, `type`

← Предыдущая тема: [3 — Примитивы и вывод типов](#тема-3--примитивы-и-вывод-типов)  
→ Следующая тема: [5 — Union, optional, `null`](#тема-5--union-optional-null)

---

### Теория с аналогией

**Аналогия: анкета и два слота в бейдже**

Как в 🔗 Junior теме 14, объект — поля. TS описывает **форму анкеты**: какие ключи и какие типы значений.

```typescript
type User = {
  name: string;
  age: number;
};

const anna: User = { name: "Анна", age: 20 };
// const bad: User = { name: "Анна" }; // нет age
```

`type` — имя для формы, чтобы не копировать фигурные скобки. Стирается, как любая аннотация (тема 1).

Массив: `User[]` или `Array<User>`. Запись разная, смысл тот же. Разбор буквы `T` в `Array<T>` — тема 9; пока достаточно `User[]`.

Как в 🔗 Junior теме 15, `map`/`filter` сохраняют тип элементов, если колбэк описан (тема 7).

**Кортеж** — массив фиксированной длины, у каждого места свой тип: `[number, string]` — «сначала id, потом название». Это не «просто `User[]` неизвестной длины».

```typescript
type Lesson = { id: number; title: string };

function lessonPair(lesson: Lesson): [number, string] {
  return [lesson.id, lesson.title];
}

const pair = lessonPair({ id: 4, title: "Объекты" });
const id = pair[0];    // number
const title = pair[1]; // string
// pair[2] — ошибка: третьего слота нет
```

Лишние поля при **прямой** записи в переменную типа `User` часто запрещены (excess property check). Отдельная переменная без аннотации, которую потом передали — правила чуть мягче; в курсе пиши объект сразу как `User`.

`Partial` из стандартной библиотеки («все поля необязательны») можно встретить в подсказках IDE. Отдельной темой не делаем: необязательность — `?` в теме 5.

### Где это в реальном коде

Список уроков: `{ id: number; title: string }[]`. Пара координат `[number, number]`. Конфиг песочницы. Тело JSON после проверки (тема 13) сводят к `type`.

### Паттерны

❌ Анонимные `{ name: string }` в пяти функциях  
✅ Одно имя `type User`  
Почему: правка возраста — в одном месте.

❌ Спорить `interface` vs `type` до темы 6  
✅ Для объекта пока `type`; сравнение инструментов — следующая тема после union  
Почему: сначала форма данных, потом два синтаксиса одной идеи.

❌ `string[][][]` без нужды; кортеж длиной 8  
✅ Плоский массив объектов; кортеж из 2–3 слотов, если порядок — контракт  
Почему: вложенность путает сужение (тема 8).

### Вопросы

**Q1: Существует ли `type User` в runtime?**  
Нет. Имя формы стирается вместе с аннотациями. В запущенном JS останется объект `{ name, age }`, как в Junior теме 14. Нельзя написать `if (x instanceof User)`. Проверка полей — обычный JS или guard (тема 10).

**Q2: Чем `User[]` отличается от `User`?**  
`User` — одна анкета. `User[]` — список анкет любой длины, каждый элемент той же формы. Пустой список законен. Индекс `users[0]` может быть `undefined` — как в Junior, даже если тип элемента `User`.

**Q3: Можно ли поле-функция в объекте?**  
Да: `greet: (name: string) => string`. Подробно — тема 7. Тип поля — контракт колбэка, не отдельный «класс». Стирается так же.

**Q4: Обязательны ли все поля `type`?**  
Пока да: нет ключа — ошибка. Необязательные помечают `?` в теме 5. Не путай с «поле есть, но значение `null`» — это `| null`, тоже тема 5.

**Q5: Нужно ли копировать объект из-за типов?**  
Нет. Ссылка та же, что в 🔗 Junior теме 16. Тип не клонирует данные и не делает объект иммутабельным. Мутация `anna.age = 21` меняет ту же анкету.

**Q6: Почему лишнее поле в литерале `{ name, age, extra }` часто красное?**  
Прямой литерал, присвоенный `User`, проверяют строго: лишний ключ обычно ошибка. Это ловит опечатки. Если сначала `const raw = { ... }` без типа, а потом передал в функцию — проверка мягче. В курсе аннотируй литерал сразу.

**Q7: Чем кортеж `[number, string]` отличается от `(number | string)[]`?**  
Кортеж: длина и порядок слотов фиксированы, `pair[0]` — число. Массив union: каждый элемент — то или другое, длина любая. Для «id и подпись всегда рядом в этом порядке» бери кортеж. Для списка смешанных id — union-массив (тема 5).

**Q8: `User[]` и `Array<User>` — разные типы?**  
Нет, это две записи одного. В теме 9 буква `T` объяснит, зачем `Array<T>` в дженериках. Сейчас выбирай, что читаемее; в примерах курса чаще `User[]`.

**Q9: Как описать вложенный объект `{ author: { name: string } }`?**  
Вложи фигурные скобки или вынеси `type Author = { name: string }` и поле `author: Author`. Второе лучше, если автор встречается дважды. Это всё ещё тема 4, не классы Middle.

**Q10: Меняет ли `type` ссылку или копирует поля?**  
Ни то ни другое в runtime: `type` исчезает. Две переменные `User` могут указывать на один объект. Форма нужна компилятору, не сборщику мусора.

### Практическое задание

В `topics/topic_4/exercises.ts`: `type Lesson` с `id` и `title`. `describeLesson` логирует `"id: title"`. `lessonPair` возвращает кортеж `[id, title]`.

### Решение с инсайтом

```typescript
export type Lesson = {
  id: number;
  title: string;
};

export function describeLesson(lesson: Lesson): void {
  console.log(`${lesson.id}: ${lesson.title}`);
}

export function lessonPair(lesson: Lesson): [number, string] {
  return [lesson.id, lesson.title];
}
```

**Инсайт:** `type` — имя формы, не коробка в памяти. Кортеж — когда важен порядок слотов, не только «массив чего-то».

## Тема 5 — Union, optional, `null`

← Предыдущая тема: [4 — Объекты, массивы, кортежи, `type`](#тема-4--объекты-массивы-кортежи-type)  
→ Следующая тема: [6 — `type` vs `interface`](#тема-6--type-vs-interface-пересечение-)

---

### Теория с аналогией

**Аналогия: вилка на дороге и пустая клетка анкеты**

**Union** `string | number` — значение одно, но вид один из двух (id с сервера иногда строка).

**Optional** `title?: string` — ключа может не быть (как «клетка не заполнена»). Это не то же, что `title: string | undefined` в деталях записи объекта, но в чтении часто рядом.

**`null` и `undefined`** — как 🔗 Junior тема 7. При `strict` нельзя положить `null` в `string` без `| null`. `querySelector` в теме 11 как раз `Element | null`.

```typescript
type Id = string | number;

function formatId(id: Id): string {
  return String(id);
}

type Draft = {
  title?: string;
};

type MaybeTitle = {
  title: string | null;
};
```

Пока не сузил union (тема 8), доступны только операции, общие для всех вариантов: для `string | number` нет `.toUpperCase()` без проверки.

Для optional в логе удобен `??` из повседневного JS: `d.title ?? "без названия"`.

### Где это в реальном коде

- `response.status` — число, текст ошибки — строка: не мешай в одну переменную без union.
- Необязательный email в форме.
- «Ещё не загрузили» — `data: User | null`.

### Паттерны

❌ `any` вместо union  
✅ Перечислить варианты `|`  
Почему: `any` выключает слой (тема 10).

❌ `string | number | boolean | null | undefined` на всё  
✅ Два-три смысла максимум  
Почему: иначе сужение нечитаемо.

❌ Игнорировать `null` у DOM  
✅ Проверка `if (!el) return`  
Почему: элемент могли не найти (🔗 Junior тема 17; тема 11).

### Вопросы

**Q1: `?` и `| undefined` — одно и то же?**  
Похожи, когда *читаешь* поле: его может не быть. При *создании* объекта `title?: string` позволяет ключ не писать. `title: string | undefined` обычно требует ключ, пусть со значением `undefined`. Для форм чаще `?`. Для «ключ всегда есть, иногда пусто» — `| null` или `| undefined` явно.

**Q2: Почему нет `.length` у `string | number`?**  
У числа нет `.length`. Компилятор разрешает только то, что верно для *всех* вариантов union. Сначала сузь через `typeof` (тема 8), потом зови методы строки. `String(id)` законен для обоих — поэтому `formatId` так и пишет.

**Q3: Зачем `| null`, если есть optional?**  
`null` — явное «пусто положили». Нет ключа — другое. DOM и `fetch` чаще отдают `null`, не «забытый ключ». Optional — «анкета ещё без этой клетки». Не склеивай оба смысла в одно поле без нужды.

**Q4: Какой тип у `let x` без значения, как в Junior?**  
`undefined`, пока не аннотируешь иначе. В strict нельзя потом присвоить строку, если вывод уже `undefined`. Пиши `let x: string | undefined` или сразу дай значение.

**Q5: Чем `(string | number)[]` отличается от кортежа `[string, number]`?**  
Массив union: каждый элемент — строка *или* число, длина любая. Кортеж из темы 4: первое всегда строка, второе всегда число. Не подменяй одно другим в голове.

**Q6: Что делает `d.title ?? "без названия"` для optional?**  
Если `title` нет или оно `null`/`undefined`, берётся запасная строка. Это runtime, как в Junior. Тип после `??` — уже `string`, если запасная строка. Не путай с `||`: пустая строка `""` для `||` ложна, для `??` — нормальное название.

**Q7: Можно ли union объектов `{ kind: "ok" } | { kind: "err" }`?**  
Да. Это заготовка к теме 12 (discriminated union). Пока достаточно: общее поле-метка потом поможет сузить. Не делай `{ data: User | null, error: string | null }` с противоречивыми комбинациями, если уже видишь два разных смысла.

**Q8: `null` и `undefined` — взаимозаменяемы в типах?**  
Нет. Это два значения Junior темы 7 и два разных варианта в union. `string | null` не принимает «забыли объявить». DOM — обычно `null`. Неинициализированная переменная — `undefined`.

**Q9: Что будет, если в union один из вариантов никогда не приходит?**  
Тип всё равно широкий, пока ты его не сузил. Лишний вариант ослабляет проверку. Не пиши `| string` «на будущее», если сервер всегда шлёт число. Узкий тип — больше помощи от `tsc`.

**Q10: Обязателен ли union на параметре `formatId`?**  
Если функция правда ест и строку, и число — да, это честный контракт. Если всегда строка — не раздувай `| number`. Union появляется от реальных входов, не от страха.

### Практическое задание

В `topics/topic_5/exercises.ts`: `formatId(id: string | number): string` — всегда строка для лога. `labelDraft(d: { title?: string })` — если нет title, лог `"без названия"`.

### Решение с инсайтом

```typescript
export function formatId(id: string | number): string {
  return String(id);
}

export function labelDraft(d: { title?: string }): void {
  console.log(d.title ?? "без названия");
}
```

**Инсайт:** `|` — честный список вариантов; `?` — поле может не прийти. Дальше компилятор заставит сузить.

## Тема 6 — `type` vs `interface`, пересечение `&`

### Теория с аналогией

**Аналогия: табличка на двери и бейдж из двух табличек**

`type` и `interface` для **объекта** часто описывают одну и ту же анкету. Разница не в runtime: оба стираются. Разница в том, *что ещё* умеет синтаксис.

```typescript
interface User {
  name: string;
  age: number;
}

type UserId = string | number;

type Greeter = (name: string) => string;
```

**`interface`** удобен для формы объекта: поля, при желании `extends` другой объектной формы.

```typescript
interface Employee extends User {
  role: "admin" | "editor";
}
```

**`type`** обязателен (в этом слое), когда форма — не только объект: union, кортеж, тип функции. `interface Id = string | number` нельзя.

**Пересечение `&`** — «обе анкеты сразу»: все поля `A` и все поля `B`.

```typescript
type User = { name: string; age: number };
type WithRole = { role: "admin" | "editor" };
type Staff = User & WithRole;

const staff: Staff = { name: "Анна", age: 20, role: "editor" };
```

`interface Employee extends User` и `type Staff = User & WithRole` для двух объектных форм близки по смыслу. Выбери одно в файле, не мешай оба стиля без нужды.

`interface` с тем же именем в двух местах *склеивает* поля (declaration merging). В этом слое не опирайся на склейку: одно имя — одно объявление. Иначе форма растёт из чужого файла, и ты не видишь полную анкету.

В Middle спросят «чем отличаются». Короткий ответ слоя: объекты — оба; union / функции / кортежи — `type`; склейку `interface` не используем как приём.

### Где это в реальном коде

- Модель пользователя в модуле: `interface User` или `type User`.
- `type Status = "idle" | "loading"` — только `type`.
- Сотрудник = пользователь + роль: `extends` или `&`.

### Паттерны

❌ Война «в проекте только interface» на первой неделе  
✅ Объект — любой из двух; union и функции — `type`  
Почему: правило из холивара здесь не учит форме данных.

❌ `interface` для `string | number`  
✅ `type Id = string | number`  
Почему: так устроен синтаксис.

❌ Два `interface User` в разных файлах «само склеится»  
✅ Одно объявление, при необходимости `extends` явно  
Почему: невидимая склейка путает.

### Вопросы

**Q1: Есть ли `interface` в запущенном JavaScript?**  
Нет. Как `type`, стирается. Браузер не знает `User`. Не путай с классами Middle: это не конструктор.

**Q2: Чем `type` отличается от `interface` для объекта `{ name: string }`?**  
Для простой анкеты почти ничем: оба задают поля. `interface` умеет `extends` и слияние одноимённых объявлений. `type` умеет union, кортежи, типы функций через `=`. Выбирай по тому, *какая* форма, не по моде.

**Q3: Можно ли написать `interface Id = string | number`?**  
Нет. Union — это `type`. То же для `(n: number) => string` как имени формы и для `[number, string]`. `interface` — про объект (и похожие сигнатуры вызова, которые в этом слое не ядро).

**Q4: Что делает `type Staff = User & { role: "admin" }`?**  
Пересечение: нужны поля `User` *и* `role`. Не хватает `age` — ошибка. Это не «или» (union `|`). «Или» — тема 5: одно значение, один из вариантов.

**Q5: `extends` у `interface` и `&` у `type` — одно и то же?**  
Для двух объектных форм смысл близкий: взять поля родителя и добавить свои. Синтаксис разный. Не смешивай в одной цепочке без нужды. Классы и `implements` — Middle, не этот слой.

**Q6: Когда в курсе брать `interface`, а когда `type`?**  
Объектная модель, которую расширяют — `interface` уместен. Union статусов, Id, тип колбэка, кортеж — `type`. Если сомневаешься на простой анкете — `type`, как в темах 4–5. Главное — не плодить два имени одной формы.

**Q7: Почему не стоит полагаться на declaration merging?**  
Два `interface User` в разных файлах сольются в одну форму. Полезно библиотекам, опасно в учебном коде: ты не видишь все поля в одном месте. Объяви один раз или явно `extends`.

**Q8: Можно ли `&` для `string & number`?**  
Тип, которому нужно быть и строкой, и числом сразу, на практике пуст (кроме экзотики). Пересечение имеет смысл у *объектов* с полями. Не склеивай примитивы через `&` «на всякий случай».

**Q9: Заменяет ли `interface` тему 4?**  
Нет. Тема 4 — форма данных: поля, массив, кортеж. Тема 6 — два синтаксиса имени и склейка форм. Кортеж и union по-прежнему через `type`.

**Q10: Спросят ли это на Middle-интервью?**  
Да, часто первым вопросом про TS. Ответ слоя достаточный: объекты оба; union/`&`/функции — `type`; merging не как привычка. Дальше Middle добавит стек и тонкости. Не учи войну «только interface в React».

### Решение с инсайтом

```typescript
export interface User {
  name: string;
  age: number;
}

export type UserId = string | number;

export type Staff = User & { role: "admin" | "editor" };

export function describeStaff(s: Staff): void {
  console.log(`${s.name}: ${s.role}`);
}
```

**Инсайт:** `interface` и `type` для объекта — таблички на одной двери; `|` и функции живут только у `type`. `&` — обе анкеты сразу.
