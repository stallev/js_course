# Раздел 1 — Слой поверх JS

Junior уже научил запускать `.js`, класть значения в `let`/`const` и собирать шаги в функции. TypeScript не новый язык с другой логикой `if` и массивов: это **тот же JavaScript плюс заметки о форме данных**, которые читает компилятор *до* запуска.

Этот раздел отвечает на два бытовых вопроса: *зачем* эти заметки и *какой командой* файл `.ts` проверить и выполнить.

### Теория с аналогией

**Аналогия: проверка орфографии до отправки письма**

JavaScript выполняет код и падает, когда уже «письмо ушло»: функция ждала строку, а пришло число — ошибка в консоли у пользователя. TypeScript — проверка черновика: редактор и `tsc` подчёркивают несовпадение *пока файл ещё у тебя*.

Как в 🔗 Junior теме 4, у значения есть тип (`typeof`). TS фиксирует ожидаемый тип **в тексте программы**, а не только в голове.

```
  файл.ts          tsc / IDE              движок JS
  (JS + типы)  →   красные ошибки     →   выполняется уже без типов
                   или «можно запускать»
```

**Типы стираются.** После проверки в файле не остаётся `string` и `number`. Браузер и Node видят обычный JS — как в 🔗 Junior теме 1.

```typescript
function greet(name: string): string {
  return "Привет, " + name;
}

greet("Анна");
// greet(42); // tsc: number не string
```

После стирания останется примерно:

```javascript
function greet(name) {
  return "Привет, " + name;
}
```

TS **не** защищает от всего: деление на ноль, сеть, опечатка в данных с сервера — это runtime, как раньше. Он ловит то, что можно сказать по форме: «эта функция ест строку».

### Где это в реальном коде

- Параметр функции формы: `value: string` из `input.value` (🔗 Junior тема 19).
- Ответ `fetch`: сначала `unknown` или свой `type`, не «любой объект» (темы 10 и 13 этого слоя; 🔗 Junior тема 23).
- Экспорт модуля: снаружи видно и JS-имя, и тип (тема 14; 🔗 Junior тема 25).

### Вопросы

**Q1: TypeScript — другой язык или слой над JavaScript?**  
Слой. Ты пишешь тот же JavaScript, что в Junior: `if`, функции, массивы. Сверху компилятор читает заметки о форме данных. После проверки эти заметки стираются, и движок выполняет обычный JS. Отдельного «рантайма TypeScript» в браузере нет.

**Q2: Когда ошибка типов проявляется — при клике пользователя или раньше?**  
Обычно раньше: в редакторе и при `tsc`, пока файл ещё у тебя. Если обойти проверку (`any`, ложный `as` — тема 10), несовпадение может всплыть уже в runtime. TS не заменяет тесты и не ловит клик сам по себе.

**Q3: Защищает ли TypeScript от пустого массива и от сетевой ошибки?**  
Нет. Он описывает форму: пустой `number[]` законен, сеть падает как в 🔗 Junior теме 23. Опечатка в JSON с сервера тоже runtime, пока ты сам не проверишь данные (тема 13). Типы — не валидация ответа.

**Q4: Почему `greet(42)` красное, а в чистом JS «работает»?**  
В JS `"Привет, " + 42` станет строкой `"Привет, 42"` — движок сложит, не спросив. TS считает вызов нарушением контракта `name: string`. Красное — не «другая арифметика», а отказ принять число туда, где обещали строку.

**Q5: Нужен ли TypeScript, если я один и файлов мало?**  
Не обязателен. Смысл появляется, когда одну функцию вызывают из нескольких мест и легко перепутать аргумент. Этот слой — привычка до Middle, а не требование для скрипта из десяти строк. Если контрактов нет, выигрыш маленький.

**Q6: Что значит «типы стираются»?**  
Аннотации нужны компилятору и редактору. В запущенном файле их нет: браузер и Node не читают `: string`. Поэтому нельзя написать `if (typeof x === MyType)` в смысле TS-типа: в runtime останется только Junior-`typeof`. Проверки «какой это объект с сервера» делай обычным JS, типы лишь описывают результат.

**Q7: Меняет ли TypeScript поведение `if`, циклов и функций?**  
Нет. Те же правила, что в Junior разделах 3–4. TS не выполняет программу иначе и не добавляет новые ветки. Он только запрещает собрать файл, если формы данных не сходятся. Если `tsc` зелёный, выполнение как у соответствующего `.js`.

**Q8: Чем аннотация `: string` отличается от `typeof` в Junior теме 4?**  
`typeof` — выражение в runtime: ярлык уже лежащего значения. Аннотация — обещание для компилятора, в запущенном JS его нет. Можно написать `: string` и всё равно положить не то, если обойти проверку. `typeof` тогда покажет, что реально пришло.

**Q9: Почему не ставят тип на каждую локальную `const`?**  
Компилятор сам видит `1` и `"Анна"` (тема 3 — вывод типов). Шум `const n: number = 1` ничего не ловит сверх этого. Аннотация нужна там, где вывода нет: параметр функции, пустой массив, граница модуля. Внутри функции дай вывести.

**Q10: Что TypeScript не обещает, даже при зелёном `tsc`?**  
Деление на ноль, таймаут, 404, опечатку в поле JSON, логическую ошибку «сложил не те числа». Он ловит несовпадение *описанной* формы: число вместо строки, забытое поле объекта, вызов без аргумента. Остальное — как в Junior: `try/catch`, проверки, тесты.

### Теория с аналогией

**Аналогия: черновик, корректор и сцена**

- **`tsc`** — корректор: читает `.ts`, ругается на типы, по желанию пишет `.js`.
- **`npx tsx файл.ts`** — сцена: проверил (через тот же мир TS) и сразу выполнил, как `node файл.js` в 🔗 Junior теме 1.
- **`tsconfig.json`** — правила корректора: `strict` включает полезные проверки, в том числе пустые значения (тема 5).

Минимальный смысл опций для этого слоя:

```json
{
  "compilerOptions": {
    "target": "ES2020",
    "module": "ES2020",
    "strict": true,
    "skipLibCheck": true
  },
  "include": ["topics/**/*.ts"]
}
```

`strict: true` — пакет строгих правил. Без него часть ошибок «молчаливая». В sandbox курса этот флаг уже включён.

**Две привычки**

```bash
# из корня js_course: выполнить упражнение
npx tsx typescript/sandbox/js_sandbox/topics/topic_2/exercises.ts

# только проверка типов всего sandbox
npx tsc -p typescript/sandbox/js_sandbox/tsconfig.json --noEmit
```

Браузер не читает `.ts`. Для раннера: `npm run bridge:watch` пишет рядом `exercises.js`, страница импортирует его — как Junior Live Server, только исходник `.ts`.

### Где это в реальном коде

- Локально: `tsx` на скрипт без сборки сайта.
- CI: `tsc --noEmit`, чтобы не влить красный файл.
- Фронт: Vite/Next сами зовут компилятор; в этом слое достаточно `tsc` + Live Server.

### Паттерны

❌ Открывать `.ts` как `file://` в браузере  
✅ Live Server после `bridge:watch`, либо только `tsx`  
Почему: нет движка TS в обычной вкладке.

❌ Выключать `strict`, чтобы «прошло»  
✅ Починить тип (темы 5, 8, 10)  
Почему: иначе слой бесполезен.

❌ Держать два разных `tsconfig` «на глаз» без `include`  
✅ Один конфиг на sandbox, как в репозитории  
Почему: иначе `tsc` не видит файлы.

### Вопросы

**Q1: Чем `tsx` отличается от `node файл.js`?**  
`node` в Junior ждёт JavaScript. `tsx` понимает синтаксис TypeScript и сразу выполняет файл `.ts`. Под капотом типы всё равно не живут в движке: `tsx` проверяет и запускает уже как JS. Для упражнений слоя это замена `node`, не замена браузера.

**Q2: Что делает `tsc --noEmit`?**  
Компилятор проверяет типы по `tsconfig` и **не** пишет файлы `.js`. Удобно в CI и локально: «можно ли влить», без папки с сборкой. Если нужен JS для Live Server, смотри `bridge:watch` — там emit как раз нужен.

**Q3: Зачем в `tsconfig` поле `target`?**  
Оно говорит, в какой диалект JS скомпилировать: `const`, стрелки, промисы. Для курса достаточно `ES2020`. Слишком старый `target` усложнит вывод; слишком новый может не открыться в древнем Node. На поведение типов `strict` влияет сильнее, чем `target`.

**Q4: Нужен ли `npm install` перед упражнениями?**  
Да, один раз в корне `js_course`: в `package.json` уже есть `typescript`. `npx tsx` подтянет `tsx`, если его ещё нет. Без установки `tsc` из проекта может не найтись, и команды из README разъедутся с версией курса.

**Q5: Если `tsc` красный, а `tsx` всё равно бежит — на что ориентироваться?**  
На `tsc -p typescript/sandbox/js_sandbox/tsconfig.json --noEmit`. Слой учит зелёные типы, а не «лишь бы консоль что-то напечатала». Расхождение инструментов бывает; красное в `tsc` чини, не выключай проверку.

**Q6: Что такое `tsconfig.json` простыми словами?**  
Список правил для `tsc`: какие файлы брать (`include`), какой JS на выходе (`target`), насколько строго проверять (`strict`). Без него компилятор угадывает или смотрит не те папки. В курсе один конфиг на sandbox — не плоди второй «чтобы прошло».

**Q7: Что включает `strict: true` на уровне этого слоя?**  
Пакет строгих проверок: нельзя молча получить `any`, `null` не считается допустимым вместо строки без явного union (тема 5). Подробные флаги — в Middle. Здесь правило одно: не выключай `strict`, чтобы упражнение «собралось».

**Q8: Почему вкладка браузера не открывает `.ts` как Junior `.js`?**  
Обычный браузер не компилирует TypeScript. Нужен шаг в `.js` (`bridge:watch`) и страница через Live Server, не `file://`. Либо работай только в терминале через `tsx`. Это та же кухня, что Junior тема 1, плюс корректор.

**Q9: Чем `npm run bridge:watch` отличается от разового `tsx`?**  
`tsx` — выполнить один файл сейчас. `bridge:watch` — держать `tsc` включённым, чтобы рядом с `.ts` появлялся `.js` для раннера. Для теории в терминале достаточно `tsx`. Для кликов на странице темы нужен watch и HTML.

**Q10: Зачем в конфиге `include`?**  
Чтобы `tsc` видел упражнения в `topics/**/*.ts` и не лез в чужие папки. Если `include` пустой или неверный, проверка молчит или ругается не на те файлы. Один явный glob надёжнее, чем «все `.ts` на диске».
