## Тема 9 — Простые дженерики и `Promise<T>`

← Предыдущая тема: [8 — Сужение](section_3_functions.md#тема-8--сужение-narrowing)  
→ Следующая тема: [10 — `any` vs `unknown`, `as`, type guard](#тема-10--any-vs-unknown-as-type-guard)

---

### Теория с аналогией

**Аналогия: коробка с этикеткой «то же, что внутри»**

`Array<number>` — коробка, внутри числа. Буква `T` в `function first<T>(items: T[]): T | undefined` — «положи этикетку с тем типом, что у элементов». Вызов `first([1, 2])` выводит `T = number`.

```typescript
function first<T>(items: T[]): T | undefined {
  return items[0];
}

const n = first([10, 20]);      // number | undefined
const s = first(["a", "b"]);    // string | undefined
```

Как в 🔗 Junior темах 21–22, промис — «значение позже». В типах это тоже коробка: `Promise<User>` — «когда дождёшься, будет `User`».

```typescript
function asPromise<T>(value: T): Promise<T> {
  return Promise.resolve(value);
}

async function demo(): Promise<number> {
  const n = await asPromise(42);
  return n;
}
```

`async` функция всегда возвращает `Promise<...>`. `await` снимает коробку: из `Promise<number>` снова `number`. Стирание (тема 1) не добавляет промис в runtime само по себе — это тот же JS, что в Junior.

Не ядро слоя: `T extends ...`, несколько параметров `K, V`, условные типы, `infer`.

### Где это в реальном коде

`Array.prototype.map` уже дженерик. Свои хелперы: `first`, `last`, `asPromise`. `fetch` вернёт `Promise<Response>`; разбор JSON — тема 13. Не пиши дженерик, если функция всегда про `string`.

### Паттерны

❌ `function first(items: any[]): any`  
✅ `function first<T>(items: T[]): T | undefined`  
Почему: связь входа и выхода.

❌ Дженерик «на всякий случай» на каждую функцию  
✅ Только когда тип кочует из аргумента в результат  
Почему: иначе код как шифр.

❌ Игнорировать `undefined` у пустого массива; забыть, что `await` даёт `T`, а не `Promise<T>`  
✅ `T | undefined` у `first`; после `await` работай с `T`  
Почему: пустой массив законен; двойной `Promise` путает.

### Вопросы

**Q1: `T` — настоящий тип в JavaScript?**  
Нет. Буква живёт только для компилятора и стирается, как аннотация темы 1. В runtime `first` — обычная функция, которая возвращает `items[0]`. Нельзя написать `if (T === number)`. Этикетка не едет в браузер.

**Q2: Чем `T[]` отличается от `Array<T>`?**  
Запись разная, смысл тот же. В теме 4 уже было `User[]`. `Array<T>` удобен, когда рядом другие дженерики (`Promise<T>`, `ReadonlyArray<T>`). Выбери один стиль в файле. Это не два разных массива в памяти.

**Q3: Зачем `| undefined` у `first`?**  
Как в Junior, `items[0]` у пустого массива — `undefined`. Если написать только `T`, солжёшь компилятору. Можно бросать ошибку осознанно — тогда тип возврата `T`, но вызывающий должен быть готов к исключению (🔗 Junior тема 10).

**Q4: Можно ли вызвать `first<string>([1, 2])`?**  
`tsc` поругается: элементы не `string`. Явный `first<string>` фиксирует `T` и проверяет аргумент. Обычно `T` выводят из массива, явный параметр нужен для пустого `first<number>([])`.

**Q5: Это те же дженерики, что в React `useState<User>`?**  
Та же идея: параметр типа, не «магия хука». Хуки и JSX — Middle. Здесь достаточно понять `first` и `Promise`. Не прыгай в `useState`, пока не кончится слой.

**Q6: Что означает `Promise<User>`?**  
Промис, который *разрешится* значением формы `User` (или упадёт — ошибка не в `T`). Сам промис ты уже знаешь из Junior. `T` — содержимое коробки «потом», не «сейчас». Без дженерика пришлось бы `Promise<any>` и тема 1 умерла.

**Q7: Что делает `await` с типом?**  
Снимает `Promise`: `await asPromise(42)` имеет тип `number`. Если забыть `await`, тип останется `Promise<number>`, и `.toFixed` будет красным. Это не новое поведение JS — TS следует за Junior `async/await`.

**Q8: Почему `async function demo()` имеет тип `Promise<number>`, хотя внутри `return n`?**  
`async` всегда оборачивает возврат в промис. Аннотация `: Promise<number>` честна. Не пиши `: number` у `async` функции — `tsc` не согласится. Синхронная `function` может вернуть `number` без коробки.

**Q9: Когда дженерик не нужен?**  
Когда вход и выход всегда одни и те же: `function greet(name: string): string`. Буква `T` имеет смысл, если *один* алгоритм для разных типов и тип надо протащить. Иначе шифр из `<T>` без выгоды.

**Q10: Связан ли `map` с этой темой?**  
Да: колбэк получает элемент типа `T`, возвращает `U`, результат — `U[]`. Ты уже вызывал `map` в Junior теме 15. Теперь видно, почему после `numbers.map(n => n * 2)` тип — числа, а не `any[]`. Свою `first` пишем тем же приёмом.

### Практическое задание

В `topics/topic_8/exercises.ts`: `first<T>(items: T[]): T | undefined` и `asPromise<T>(value: T): Promise<T>`. Залогируй первый элемент `[3, 1, 2]` и `["б", "а"]`; `await asPromise(42)`.

### Решение с инсайтом

```typescript
export function first<T>(items: T[]): T | undefined {
  return items[0];
}

export function asPromise<T>(value: T): Promise<T> {
  return Promise.resolve(value);
}
```

**Инсайт:** дженерик связывает тип входа с типом выхода. `Promise<T>` — та же этикетка, только «потом».

### Что дальше

Самая частая дыра — `any`. Рядом — честный `unknown`, опасный `as` и guard. Тема 10.

## Тема 10 — `any` vs `unknown`, `as`, type guard

← Предыдущая тема: [9 — Простые дженерики и `Promise<T>`](#тема-9--простые-дженерики-и-promiset)  
→ Следующая тема: [11 — DOM-типы](#тема-11--dom-типы-element--null)

---

### Теория с аналогией

**Аналогия: выключить сигнализацию vs коробка «не открывать без проверки» vs табличка «поверь мне»**

`any` — сигнализация выключена: можно вызывать что угодно, слой TypeScript перестал работать (тема 1).

`unknown` — коробка: значение есть, но пока не сузил (тема 8), нельзя звать методы.

`as` — табличка на коробке без открытия: компилятор верит, runtime не проверяет.

Type guard — функция с предикатом `x is string`: внутри `if` тип уже, потому что проверка *реально* произошла.

```typescript
function isString(x: unknown): x is string {
  return typeof x === "string";
}

function asString(raw: unknown): string {
  if (isString(raw)) {
    return raw;
  }
  return "";
}

// опасно: никакой проверки
function lie(raw: unknown): number {
  return raw as number;
}
```

`JSON.parse` в старых lib часто даёт `any`. В этом слое сразу считай результат `unknown` и сужай. Полный разбор ответа `fetch` — тема 13.

Не ядро: сложные guards на все поля объекта сразу — достаточно `typeof` и `in`, как в теме 8.

### Где это в реальном коде

- Тело `JSON.parse`, `localStorage`, сообщение `postMessage`.
- `catch (e)` при `strict`: `e` часто `unknown`.
- Граница старого `.js` модуля — не оставляй `any` навсегда.

### Паттерны

❌ `const data: any = JSON.parse(text)`  
✅ `unknown` + сужение или guard  
Почему: сервер и строка не обязаны соблюдать твой `type`.

❌ `raw as User` «чтобы прошло»  
✅ `isString` / проверка полей; `as` только если источник уже сужен  
Почему: `as` не валидатор.

❌ Guard без `x is T` (`boolean` вместо предиката)  
✅ `x is string` в возврате  
Почему: иначе внутри `if` тип не сузится.

### Вопросы

**Q1: Когда `any` допустим в этом слое?**  
Почти никогда. Временный костыль на границе неудобного `.js` — с планом убрать. Каждое `any` заражает выражения вокруг: методы «есть», пока программа не упадёт. Если не знаешь тип — `unknown`, не `any`.

**Q2: Чем `unknown` лучше `any`?**  
Оба принимают любое значение на вход. С `unknown` нельзя сразу звать `.toUpperCase`: нужен narrowing или guard. С `any` компилятор молчит. `unknown` сохраняет смысл темы 1; `any` её отменяет.

**Q3: Что делает `as number`?**  
Утверждение типа: «считай, что это число». Нет проверки в runtime. Если пришла строка, `tsc` зелёный, пользователь видит `NaN` или исключение. Используй, когда сужение уже сделано и осталась узкая дыра, не вместо `typeof`.

**Q4: Чем type guard отличается от `as`?**  
Guard выполняет проверку и в сигнатуре говорит `x is T`. После `if (isString(x))` внутри блока `x` — строка. `as` проверки не делает. Guard можно составить из Junior-`typeof`. Это безопасный мост к данным снаружи.

**Q5: Почему `function isString(x: unknown): boolean` слабее предиката?**  
Вернёт правда/ложь в runtime, но TypeScript **не** сузит `x` в `if`. Нужна фраза `x is string`. Без неё придётся сужать вручную ещё раз. Предикат — контракт для компилятора, не новый JS.

**Q6: `as` и сужение темы 8 — одно и то же?**  
Нет. Сужение следует за `if` / `typeof`. `as` — приказ не следовать. В теме 8 мы как раз запрещали `as` «чтобы замолчать». Здесь видно, зачем он всё же существует: узкие места после реальной проверки, не вместо неё.

**Q7: Как типизировать `catch (e)`?**  
В `strict` часто `unknown`. Не зови `e.message`, пока не проверишь `e instanceof Error` или форму объекта. Не пиши `catch (e: any)`. Это та же коробка, что JSON снаружи.

**Q8: Заражает ли `any` соседние переменные?**  
Да. Поле `any` в объекте, возврат `any`, аргумент `any` — дальше вывод часто становится `any`, и красных нет. Один `any` на границе может выключить полфайла. Лечи сразу, не «потом в конце спринта».

**Q9: Нужен ли guard, если уже `typeof x === "string"` в том же `if`?**  
Для одной проверки — достаточно `if` темы 8. Guard полезен, когда ту же проверку повторяешь в трёх функциях или хочешь имя `isString`. Не плоди предикаты на каждую строку кода.

**Q10: Связь с `fetch` и темой 13?**  
Ответ сети — данные снаружи, для компилятора сначала `unknown`. Тема 10 даёт инструменты: не `any`, не голый `as User`. Тема 13 соберёт их в разбор JSON. Не объявляй `res.json()` как `Promise<User>` без проверки.

### Практическое задание

В `topics/topic_10/exercises.ts`: `isString(x: unknown): x is string` и `asString(raw: unknown): string` (строка как есть, иначе `""`). Не используй `any`.

### Решение с инсайтом

```typescript
export function isString(x: unknown): x is string {
  return typeof x === "string";
}

export function asString(raw: unknown): string {
  return isString(raw) ? raw : "";
}
```

**Инсайт:** `unknown` честен; guard сужает; `as` и `any` прячут дыру.

## Тема 11 — DOM-типы: `Element | null`

← Предыдущая тема: [10 — `any` vs `unknown`, `as`, type guard](#тема-10--any-vs-unknown-as-type-guard)  
→ Следующая тема: [12 — Discriminated union и `never`](section_5_boundaries.md#тема-12--discriminated-union-и-never)

---

### Теория с аналогией

**Аналогия: полка в магазине — ценник есть, товара может не быть**

Как в 🔗 Junior теме 17, `querySelector` ищет узел. TypeScript не обещает, что узел на месте: тип **`Element | null`**. Это union темы 5, сужение темы 8, не «магия DOM».

```typescript
const el = document.querySelector("#title");
// el: Element | null

if (!el) {
  return;
}
el.textContent = "Готово";
```

После проверки `el` уже не `null`. Без проверки `.textContent` красное или опасно.

`document` есть только в браузере. В Node ветку с DOM не вызывай (как в Junior sandbox). В `tsconfig` курса `lib` включает `DOM`, поэтому `tsc` знает `document`.

Утверждение `el!` («точно не null») — родственник `as`: табличка без проверки. Не ставь `!` вместо `if (!el) return`.

Иногда нужен не любой `Element`, а поле ввода: `HTMLInputElement`. Тогда `instanceof HTMLInputElement` или более узкий селектор + проверка. Не ядро: полный список HTML-интерфейсов. Достаточно `Element | null` и честный early return.

### Где это в реальном коде

- `querySelector` / `getElementById`.
- Обработчик клика: цель события — узел, который может быть не тем тегом (🔗 Junior тема 18).
- Смена текста заголовка в упражнении `#title`.

### Паттерны

❌ `document.querySelector("#title")!` везде  
✅ `if (!el) return`  
Почему: `!` — обещание без проверки.

❌ `as HTMLInputElement` на любой селектор  
✅ Проверка или `instanceof`  
Почему: нашёл `div` — не поле ввода.

❌ Игнорировать ветку Node в sandbox  
✅ `if (typeof document === "undefined") return`  
Почему: `tsx` в терминале без страницы.

### Вопросы

**Q1: Почему `querySelector` не возвращает сразу `HTMLElement`?**  
Селектор может ничего не найти → `null`. Найденный узел в типах — `Element`, не обязательно конкретный тег. Это честный union, не недоделка браузера. Как в Junior: сначала проверь, что узел есть.

**Q2: Что даёт `lib: ["DOM"]` в tsconfig?**  
Описания `document`, `Element`, `querySelector` для `tsc`. Без DOM-lib редактор не знает эти имена в `.ts`. В sandbox курса библиотека уже включена. Браузер всё равно нужен, чтобы код *выполнить*.

**Q3: Чем `getElementById` похож на `querySelector`?**  
Оба могут вернуть `null`. Разница API Junior, не «другой null». Сужение то же: `if (!node) return`. Не думай, что id «всегда на странице», если HTML пишет другой человек.

**Q4: Когда уместен `el!`?**  
Почти никогда в этом слое. Это non-null assertion, родственник `as` темы 10. Имеет смысл, если строкой выше ты уже искал и знаешь, что узел на месте — всё равно лучше сохранить `if`. Не глуши красное восклицанием.

**Q5: Почему после `if (!el) return` можно писать `el.textContent`?**  
Early return сузил union: ниже `el` — `Element`. Это тема 8 на DOM. Если проверка в другой функции без guard, компилятор может не сузить. Держи поиск и использование рядом.

**Q6: Нужен ли `HTMLElement` вместо `Element`?**  
Часто достаточно `Element` для `textContent`. Для `.value` у инпута нужен более узкий тип. Тогда `instanceof HTMLInputElement` после поиска. Не кастуй `as HTMLInputElement` на `#title` с заголовком.

**Q7: Связь с темой 10?**  
`null` — не `unknown`, но та же идея «дыры на границе». Не затыкай её `any` и не ври через `as HTMLElement`. Сначала сузь, потом меняй DOM. Данные с сервера — тема 13, узлы страницы — эта тема.

**Q8: Можно ли вызывать `fillTitle` из `npx tsx`?**  
Файл запустится, но `document` нет. В упражнении ветка «открой browser/index.html». Для кликов нужен `bridge:watch` и Live Server, как в теме 2. Это не баг типов — другая кухня Junior темы 1.

**Q9: Меняет ли TypeScript поведение `querySelector` в runtime?**  
Нет. Типы стираются. Браузер как в Junior ищет CSS-селектор. TS только не даёт забыть про `null` *до* запуска, если ты не обошёл проверку.

**Q10: Что дальше после DOM-типов?**  
Раздел 5: взаимоисключающие состояния (тема 12), `fetch`/JSON (тема 13), `export type` (тема 14). Потом Middle, если нужен React. Слой моста ещё не кончен: границы данных важнее, чем «умею дженерик».

### Практическое задание

В `topics/topic_9/exercises.ts` (DOM-раннер): `fillTitle()` — найди `#title`; если нет — `return`; иначе `textContent = "TS"`. В терминале без `document` залогируй, что нужна страница.

### Решение с инсайтом

```typescript
export function fillTitle(): void {
  if (typeof document === "undefined") {
    console.log("открой browser/index.html");
    return;
  }
  const el = document.querySelector("#title");
  if (!el) {
    return;
  }
  el.textContent = "TS";
}
```

**Инсайт:** `Element | null` — честная дыра поиска. `if (!el)` сужает; `!` и `as` прячут промах селектора.
