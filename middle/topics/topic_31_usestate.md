## 1. Теория с аналогиями

**Аналогия: ежедневник с закладкой**

Представь ежедневник, в котором на каждой странице ты записываешь текущее значение счётчика посетителей. Ты не помнишь значение "в голове" — ты его каждый раз читаешь со страницы. Когда значение меняется, ты не зачёркиваешь старую запись — ты **открываешь новую страницу** с новым значением, а старую оставляешь как есть (историю). `useState` — это и есть "страница ежедневника", которую React хранит за пределами тела функции-компонента и открывает на нужном месте при каждом рендере.

**Зачем нужен `useState`, если это просто функция**

Функция компонента вызывается заново при каждом рендере — обычная локальная переменная (`let count = 0`) была бы создана с нуля при каждом вызове и не "помнила" бы предыдущее значение:

```typescript
// ❌ Так state не работает — count всегда 0 при каждом рендере
function Counter() {
  let count = 0;
  return <button onClick={() => count++}>Счёт: {count}</button>;
  // count++ не вызывает ре-рендер и "забывается" на следующем вызове функции
}

// ✅ useState хранит значение снаружи функции, в самом React (в Fiber-узле)
function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(count + 1)}>Счёт: {count}</button>;
}
```

**Как React находит "своё" состояние — через порядковый индекс**

```javascript
// Упрощённая модель того, что происходит внутри React
function createHookSystem() {
  const stateSlots = [];  // живёт в Fiber-узле компонента, не в теле функции
  let callIndex = 0;

  function useState(initialValue) {
    const index = callIndex++;
    if (!(index in stateSlots)) {
      stateSlots[index] = initialValue;
    }
    const setState = (newValue) => {
      stateSlots[index] = typeof newValue === 'function'
        ? newValue(stateSlots[index])
        : newValue;
      scheduleRerender();
    };
    return [stateSlots[index], setState];
  }

  return { useState, resetIndexBeforeRender: () => { callIndex = 0; } };
}
```

`callIndex` сбрасывается в 0 перед каждым рендером, а увеличивается на 1 при каждом вызове `useState`/`useEffect`/... Именно поэтому **порядок вызовов хуков должен быть одинаковым на каждом рендере** — если между двумя рендерами число вызовов `useState` меняется (например, из-за `if` перед хуком), React присвоит значения не тем "ячейкам".

```typescript
// ❌ КРИТИЧЕСКАЯ ошибка: условный вызов хука
function Bad({ showExtra }: { showExtra: boolean }) {
  const [a, setA] = useState(0);
  if (showExtra) {
    const [b, setB] = useState(0); // ❌ Правило хуков нарушено
  }
  const [c, setC] = useState(0);
  // Если showExtra меняется между рендерами — индекс c "съезжает",
  // React присвоит c значение, которое раньше принадлежало b
}
```

**Три ключевых механики `useState`**

1. **Батчинг** — несколько вызовов `setState` в одном обработчике события объединяются в один ре-рендер (🔗 Тема 1 — Event Loop, React 18 использует `queueMicrotask` для автоматического батчинга даже в `setTimeout`/промисах).

```typescript
function handleClick() {
  setCount(c => c + 1);
  setName('Alice');
  // React 18: один ре-рендер с обоими изменениями, а не два подряд
}
```

2. **Референциальное сравнение `Object.is`** — если новое значение `Object.is`-равно старому, React пропускает ре-рендер этого компонента (но хук всё равно выполнится).

```typescript
const [user, setUser] = useState({ name: 'Alice' });
setUser(user); // тот же объект по ссылке → React НЕ ре-рендерит (🔗 Тема 5)
setUser({ ...user }); // новый объект → React ре-рендерит, даже если содержимое идентично
```

3. **Функциональное обновление `setState(prev => ...)`** — гарантированно работает с актуальным значением, а не "замороженным" в замыкании (🔗 Тема 3):

```typescript
function handleTripleClick() {
  setCount(count + 1); // count — значение из ЭТОГО рендера, все три вызова видят одно и то же
  setCount(count + 1);
  setCount(count + 1);
  // Итог: +1, а не +3! Все три вызова "видят" одинаковый count из замыкания

  setCount(prev => prev + 1); // каждый вызов получает актуальное значение из предыдущего
  setCount(prev => prev + 1);
  setCount(prev => prev + 1);
  // Итог: +3 ✓
}
```

**Ленивая инициализация**

```typescript
// ❌ Плохо: expensiveComputation() выполняется на КАЖДОМ рендере,
// хотя результат используется только при первом
const [state, setState] = useState(expensiveComputation());

// ✅ Хорошо: функция вызывается React'ом только один раз — при монтировании
const [state, setState] = useState(() => expensiveComputation());
```

## 2. Связь со стеком

**TypeScript: явная типизация состояния**

```typescript
// Примитивы — тип выводится автоматически
const [count, setCount] = useState(0); // number

// Объекты/union-типы — явная типизация через generic
const [user, setUser] = useState<User | null>(null);

interface FormState {
  email: string;
  errors: string[];
}
const [form, setForm] = useState<FormState>({ email: '', errors: [] });

// Иммутабельное обновление части объекта (🔗 Тема 5, Тема 19)
setForm(prev => ({ ...prev, email: 'new@example.com' }));
```

**Next.js: `useState` работает только в Client Components**

```typescript
'use client'; // обязательная директива — useState недоступен в Server Components

import { useState } from 'react';

export function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(c => c + 1)}>{count}</button>;
}
```

Server Component не может хранить интерактивное состояние — он рендерится один раз на сервере и не "живёт" в браузере между взаимодействиями пользователя.

**Замыкания — фундамент, на котором построен `useState`**

Как обсуждалось в Теме 3, `setState`-функция — это замыкание, "помнящее" индекс своей ячейки в Fiber-узле. Понимание темы Scope и замыканий — прямой путь к пониманию того, почему stale closures (устаревшие значения в колбэках) — частый источник багов с `useState` внутри `setTimeout`/`setInterval`.

## 3. Лучшие паттерны

**✅ Паттерн 1: Функциональное обновление, когда новое значение зависит от старого**

```typescript
// ❌ Плохо: зависит от значения из замыкания текущего рендера — риск stale closure
function increment() {
  setCount(count + 1);
}

// ✅ Хорошо: всегда актуальное значение, безопасно даже в асинхронных колбэках
function increment() {
  setCount(prev => prev + 1);
}

useEffect(() => {
  const id = setInterval(() => setCount(prev => prev + 1), 1000); // ✓ работает корректно
  return () => clearInterval(id);
}, []); // пустой массив зависимостей — count из замыкания был бы "замороженным" (🔗 Тема 33)
```

*Почему best practice:* Функциональное обновление не зависит от значения, захваченного в замыкании обработчика — React передаёт актуальное значение из внутреннего хранилища напрямую.

**✅ Паттерн 2: Не хранить в state то, что можно вычислить из пропсов/другого state**

```typescript
// ❌ Плохо: дублирование источника правды — fullName может "разойтись" с firstName/lastName
function Profile({ firstName, lastName }: Props) {
  const [fullName, setFullName] = useState(`${firstName} ${lastName}`);
  // При изменении firstName/lastName снаружи fullName не обновится!
}

// ✅ Хорошо: вычисляемое значение — просто переменная в теле функции
function Profile({ firstName, lastName }: Props) {
  const fullName = `${firstName} ${lastName}`; // всегда синхронизировано
}
```

*Почему:* Каждый лишний `useState` — потенциальный источник рассинхронизации ("derived state antipattern"). Правило: если значение можно вычислить синхронно из существующих props/state — не сохраняй его в отдельном state.

**✅ Паттерн 3: Разделяй state на независимые примитивы, а не один большой объект (когда части меняются независимо)**

```typescript
// ❌ Не всегда плохо, но требует spread на каждое обновление одного поля
const [form, setForm] = useState({ name: '', email: '', age: 0 });
setForm(prev => ({ ...prev, name: 'Alice' })); // приходится копировать весь объект

// ✅ Альтернатива для полностью независимых полей — раздельные state
const [name, setName] = useState('');
const [email, setEmail] = useState('');
const [age, setAge] = useState(0);
```

*Почему:* Раздельные примитивы проще читать и обновлять без риска забыть spread; объединённый объект оправдан, когда поля логически связаны и часто обновляются вместе (например, координаты `{ x, y }`) — выбор зависит от связности данных, а не догмы.

## 4. Вопросы интервью

**Q1: Зачем нужен `useState`, если можно использовать обычную переменную?**

Обычная переменная создаётся заново при каждом вызове функции-компонента и не переживает следующий рендер. `useState` хранит значение вне тела функции — в связанном с компонентом Fiber-узле — и возвращает его на каждом новом рендере, плюс предоставляет `setState`, который планирует новый рендер.

**Q2: Как React находит "своё" значение состояния при вызове `useState`?**

По порядковому индексу вызова — React ведёт список "ячеек" состояния для каждого компонента и увеличивает счётчик при каждом вызове хука. Это работает надёжно только если хуки вызываются в одинаковом порядке на каждом рендере — отсюда правило "не вызывать хуки условно/в циклах".

**Q3: Что произойдёт, если вызвать `setState` с тем же значением, что уже в state?**

React сравнивает новое значение со старым через `Object.is`. Если они равны — ре-рендер этого компонента пропускается (bail out), хотя сам хук всё равно был вызван. Для объектов/массивов сравнение по ссылке — новый объект с идентичным содержимым всё равно триггерит ре-рендер.

**Q4: В чём разница `setCount(count + 1)` трижды и `setCount(prev => prev + 1)` трижды?**

Первый вариант — все три вызова читают одно и то же значение `count` из замыкания текущего рендера, поэтому итоговый эффект — только `+1`. Второй — функциональное обновление, каждый вызов получает актуальное на тот момент значение, поэтому эффект накопительный — `+3`.

**Q5: Что такое батчинг обновлений и как он изменился в React 18?**

Батчинг — объединение нескольких `setState` в одном событии в единый ре-рендер вместо серии отдельных. До React 18 батчинг работал только внутри React-обработчиков событий; в setTimeout/промисах каждый `setState` вызывал отдельный ре-рендер. React 18 ввёл автоматический батчинг везде — независимо от того, откуда вызван `setState` (🔗 Тема 1 — Event Loop, `queueMicrotask`).

**Q6: Зачем передавать функцию в `useState(() => ...)`, а не прямое значение?**

Ленивая инициализация: React вызовет эту функцию только один раз — при первом монтировании. Если передать прямое значение вычисления (`useState(expensiveFn())`), функция будет вызываться на **каждом** рендере, хотя результат используется только для инициализации.

**Q7: Можно ли хранить в `useState` объект и мутировать его напрямую (`state.field = x`)?**

Нельзя — React определяет необходимость ре-рендера по сравнению ссылок (`Object.is`). Прямая мутация не меняет ссылку на объект, поэтому React не узнает об изменении и не перерисует компонент. Нужно всегда создавать новый объект/массив через spread или иммутабельные операции (🔗 Тема 5, Тема 27).

**Q8: Что такое "derived state" и почему это антипаттерн?**

Хранение в `useState` значения, которое можно синхронно вычислить из существующих props/state (например, `fullName` из `firstName`+`lastName`). Это создаёт два независимых источника правды, которые могут разойтись при изменении исходных данных. Правильный подход — вычислять производное значение как обычную переменную в теле компонента (при необходимости — мемоизировать через `useMemo`, 🔗 Тема 35).

**Q9: Почему `useState` внутри `setInterval` может "не считать" правильно?**

Классический stale closure (🔗 Тема 3, Тема 8): колбэк `setInterval`, созданный при монтировании эффекта с пустым массивом зависимостей, замыкает значение state на момент создания и не видит последующих обновлений. Решение — функциональное обновление `setCount(prev => prev + 1)`, которое не зависит от значения из замыкания.

**Q10: Что вернёт `useState()` без начального значения?**

`[undefined, setState]` — React допускает вызов без аргумента, начальное значение будет `undefined`. На практике почти всегда передаётся явное начальное значение или `null` с явной типизацией (`useState<User | null>(null)`) для предсказуемости и типобезопасности.

## 5. Практическое задание

Реализуй хук `useCounter(initial, step)`, возвращающий объект `{ count, increment, decrement, reset }`:

1. `increment`/`decrement` изменяют `count` на `step` (по умолчанию 1), используя функциональное обновление.
2. `reset` возвращает `count` к исходному `initial`.
3. Три быстрых последовательных вызова `increment()` в одном обработчике должны корректно суммироваться (без stale closure).
4. Типизируй хук на TypeScript с generic для типа шага (число).

## 6. Решение с инсайтом

```typescript
import { useState, useCallback } from 'react';

interface UseCounterResult {
  count: number;
  increment: () => void;
  decrement: () => void;
  reset: () => void;
}

function useCounter(initial: number = 0, step: number = 1): UseCounterResult {
  const [count, setCount] = useState(initial);

  // Функциональное обновление — безопасно при множественных вызовах подряд
  const increment = useCallback(() => {
    setCount(prev => prev + step);
  }, [step]);

  const decrement = useCallback(() => {
    setCount(prev => prev - step);
  }, [step]);

  const reset = useCallback(() => {
    setCount(initial); // прямое значение — reset не зависит от предыдущего count
  }, [initial]);

  return { count, increment, decrement, reset };
}

// Использование
function CounterDemo() {
  const { count, increment, decrement, reset } = useCounter(0, 1);

  function handleTripleIncrement() {
    increment(); // +1
    increment(); // +1 (не "теряется" — функциональное обновление)
    increment(); // +1
    // Итог: +3, корректно, несмотря на батчинг React 18
  }

  return (
    <div>
      <p>Счёт: {count}</p>
      <button onClick={increment}>+{1}</button>
      <button onClick={decrement}>-{1}</button>
      <button onClick={handleTripleIncrement}>+3 сразу</button>
      <button onClick={reset}>Сброс</button>
    </div>
  );
}

export default useCounter;
```

> **Инсайт:** Функциональное обновление `setCount(prev => prev + step)` — не стилистическое предпочтение, а необходимость: без него `handleTripleIncrement` увеличил бы счётчик только на `+1`, потому что все три вызова `increment` в одном обработчике события читали бы одно и то же значение `count` из замыкания текущего рендера (батчинг React 18 усиливает эту ловушку, объединяя обновления). `useCallback` вокруг возвращаемых функций (🔗 Тема 35) предотвращает лишние ре-рендеры компонентов, получающих `increment`/`decrement` как пропсы.
