## 1. Теория с аналогиями

**Аналогия: черновик и чистовик**

Художник, прежде чем писать картину маслом на холсте (реальный DOM — дорогая операция, вызывает перерисовку экрана), делает набросок карандашом на бумаге (Virtual DOM — дёшево создавать и сравнивать). Когда набросок готов, художник сравнивает его с предыдущим наброском и переносит на холст **только те штрихи, которые изменились** — а не перерисовывает картину с нуля.

```
Состояние изменилось
        │
        ▼
┌─────────────────────┐
│  Новое Virtual DOM   │  ← дешёвое дерево JS-объектов
│  (снова весь рендер)│
└──────────┬───────────┘
           │ сравнение (diffing)
           ▼
┌─────────────────────┐
│  Старое Virtual DOM  │  ← дерево с прошлого рендера
└──────────┬───────────┘
           │ вычислен минимальный набор изменений
           ▼
┌─────────────────────┐
│    Реальный DOM      │  ← дорогая операция, минимальные точечные правки
└─────────────────────┘
```

**Почему прямая работа с DOM медленная**

Каждое изменение реального DOM может вызвать reflow (пересчёт геометрии) и repaint (перерисовку пикселей) — дорогие операции, блокирующие главный поток. Если менять DOM 1000 раз за цикл рендера, браузер может пересчитывать layout 1000 раз. Virtual DOM позволяет: посчитать все изменения "в уме" (в JS-объектах), затем применить их **одним батчем**.

**Что такое Virtual DOM на самом деле**

Это не какая-то отдельная "виртуальная копия браузерного DOM" — это просто дерево обычных JS-объектов вида `{ type, props, children }`, которое возвращает `React.createElement` (🔗 Тема 29):

```javascript
// JSX: <ul><li key="1">A</li><li key="2">B</li></ul>
// Virtual DOM дерево:
{
  type: 'ul',
  props: {
    children: [
      { type: 'li', key: '1', props: { children: 'A' } },
      { type: 'li', key: '2', props: { children: 'B' } },
    ]
  }
}
```

**Алгоритм diffing — эвристики O(n), а не наивные O(n³)**

Точное сравнение двух произвольных деревьев — задача с экспоненциальной сложностью. React использует эвристики, которые дают O(n) и покрывают 99% реальных UI-сценариев:

```
Правило 1 — разные типы корня → пересоздать поддерево целиком
  <div> → <span>   ⇒  старый <div> со всем содержимым удаляется,
                       <span> создаётся с нуля (даже если внутри то же самое)

Правило 2 — одинаковый тип → обновить только изменившиеся атрибуты
  <div className="a" /> → <div className="b" />
  ⇒ переиспользовать DOM-узел <div>, поменять только className

Правило 3 — списки детей сравниваются по key
  Без key: сравнение по позиции (index) — ошибочно при reorder
  С key:   React находит "тот же" элемент по key, даже если он передвинулся
```

**Пример: почему key критичен**

```
Без key (сравнение по позиции):
  Было:  [Иван, Мария, Пётр]
  Стало: [Пётр, Иван, Мария]     ← Пётр переставлен в начало

  React видит по позиции: элемент[0] был "Иван", стал "Пётр"
  → React МУТИРУЕТ текст в существующем DOM-узле, а не переставляет узлы
  → Если внутри li был <input> с фокусом — фокус "прыгнет" на неправильный элемент

С key="id" (сравнение по идентичности):
  React находит элемент с key="petr-id" в обоих деревьях
  → Понимает: это тот же элемент, просто передвинутый → перемещает DOM-узел
  → Внутреннее состояние и фокус элемента сохраняются
```

**Fiber — архитектура рендеринга с 2017 года (React 16+)**

До Fiber реконсиляция была рекурсивной и **синхронной**: если дерево большое, стек вызовов не может быть прерван — рендер блокирует главный поток целиком, пока не обработает всё дерево (аналогично проблеме из Темы 1 — Event Loop, длинная macrotask блокирует рендер кадра).

Fiber переписал реконсиляцию как **связный список узлов с возможностью прерывания**:

```
Дерево компонентов          Fiber-дерево (linked list)
      App                    Fiber{ type: App,
     /   \                          child: →Header,
Header  Content                     sibling: null }
                             Fiber{ type: Header,
                                    child: null,
                                    sibling: →Content,
                                    return: →App }
```

Каждый Fiber-узел — единица работы. React обрабатывает узлы порциями, между порциями отдаёт управление браузеру (проверяет: есть ли более приоритетная задача — например, ввод пользователя?) — почти как `processInChunks` из Темы 1.

**Две фазы: Render и Commit**

```
┌─────────────── RENDER PHASE ───────────────┐   ┌── COMMIT PHASE ──┐
│  Может быть прервана и перезапущена        │   │  Синхронная,      │
│  Вызывает функции компонентов               │   │  непрерываемая    │
│  Вычисляет diff (что изменилось)           │   │  Применяет изменения│
│  НЕ трогает реальный DOM                    │   │  в реальный DOM   │
│  "Чистая" — без побочных эффектов           │   │  Вызывает useEffect│
└──────────────────────────────────────────────┘   └───────────────────┘
```

Именно поэтому тело функции-компонента должно быть **чистым** (без побочных эффектов, мутаций, запросов) — React может вызвать его несколько раз в render-фазе (в т.ч. отменить недоделанный рендер), а побочные эффекты обязаны идти в `useEffect`, который вызывается только в commit-фазе (🔗 Тема 33).

## 2. Связь со стеком

**React 18 — конкурентный рендеринг на базе Fiber**

Прерываемость Fiber-рендера — фундамент для `useTransition`/`useDeferredValue` (🔗 Тема 38): React может начать рендерить "высокий приоритет" (ввод в поле), приостановить менее приоритетный рендер (тяжёлый список), и вернуться к нему позже.

```typescript
// React может прервать рендер большого списка,
// чтобы немедленно ответить на ввод пользователя
const [query, setQuery] = useState('');
const [isPending, startTransition] = useTransition();

function handleChange(e: React.ChangeEvent<HTMLInputElement>) {
  setQuery(e.target.value);           // высокий приоритет — обновить сразу
  startTransition(() => {
    setFilteredList(filterBigList(e.target.value)); // низкий приоритет — можно отложить
  });
}
```

**Next.js: реконсиляция работает одинаково на клиенте после гидратации**

Server Components рендерятся в HTML на сервере; после гидратации Client Components на странице продолжают использовать тот же Virtual DOM + Fiber механизм для последующих обновлений в браузере.

**React DevTools Profiler — визуализация того, что мы изучили**

Вкладка "Highlight updates" в React DevTools буквально подсвечивает DOM-узлы, которые React решил обновить после diffing — прямая визуализация алгоритма реконсиляции из этой темы.

## 3. Лучшие паттерны

**✅ Паттерн 1: Стабильный `key`, никогда `Math.random()` или index при изменяемых списках**

```typescript
// ❌ Плохо: новый key на каждом рендере — React считает все элементы новыми
{items.map(item => <Item key={Math.random()} data={item} />)}
// Результат: React удаляет и создаёт все DOM-узлы заново на каждом рендере — теряется состояние, фокус, анимации

// ✅ Хорошо: key из стабильных данных
{items.map(item => <Item key={item.id} data={item} />)}
```

*Почему best practice:* `key` — единственный сигнал React о "тождественности" элемента между рендерами. Нестабильный `key` полностью убивает пользу от Virtual DOM для этого списка.

**✅ Паттерн 2: Разные типы контента — `key`, чтобы форсировать пересоздание, а не сравнение**

```typescript
// Проблема: у двух разных пользователей одна и та же форма — состояние полей "утекает"
function ProfileForm({ userId }: { userId: string }) {
  const [name, setName] = useState('');
  // При смене userId React видит тот же тип <ProfileForm>, тот же компонент —
  // state не сбрасывается автоматически!
  return <input value={name} onChange={e => setName(e.target.value)} />;
}

// ✅ Хорошо: key форсирует React считать это НОВЫМ элементом → полный ремоунт
<ProfileForm key={userId} userId={userId} />
```

*Почему:* Смена `key` — официальный React-приём "сбросить состояние компонента", потому что при разных `key` React не пытается сравнивать/обновлять старое поддерево — он размонтирует старое и монтирует новое с нуля.

**✅ Паттерн 3: Не мутировать DOM напрямую мимо React**

```typescript
// ❌ Плохо: прямая мутация через ref, минуя Virtual DOM
function Bad() {
  const ref = useRef<HTMLDivElement>(null);
  useEffect(() => {
    ref.current!.innerHTML = '<p>Хардкод</p>'; // React не знает об этом изменении
  }, []);
  return <div ref={ref} />;
}

// ✅ Хорошо: контент выводится через JSX — Virtual DOM остаётся источником правды
function Good({ content }: { content: string }) {
  return <div>{content}</div>;
}
```

*Почему:* Если реальный DOM изменён мимо Virtual DOM, следующий diff React будет сравнивать со своим "устаревшим представлением" — реальный и виртуальный DOM расходятся, следующее обновление может отменить ручные изменения или привести к рассинхронизации.

## 4. Вопросы интервью

**Q1: Что такое Virtual DOM?**

Дерево обычных JS-объектов, описывающих желаемую структуру UI (тип узла, пропсы, дети) — результат вызова `React.createElement`. Это не копия браузерного DOM API, а лёгковесное представление, с которым дёшево работать (создавать, сравнивать), в отличие от дорогих операций с реальным DOM.

**Q2: Зачем нужен Virtual DOM, если можно менять DOM напрямую?**

Прямые множественные изменения реального DOM вызывают многократные reflow/repaint. Virtual DOM позволяет вычислить весь набор изменений "в уме" за один проход и применить их к реальному DOM одним батчем — минимизируя количество дорогих операций с браузером.

**Q3: Как работает алгоритм diffing (реконсиляция)?**

React сравнивает новое Virtual DOM дерево со старым по трём эвристикам: (1) разный тип корневого элемента → пересоздать поддерево целиком; (2) одинаковый тип → обновить только изменившиеся пропсы/атрибуты, переиспользовав DOM-узел; (3) списки детей сравниваются по `key`, а не по позиции.

**Q4: Зачем нужен `key` и что произойдёт без него?**

`key` — стабильный идентификатор элемента списка для сопоставления между рендерами. Без него React по умолчанию сравнивает по индексу — при вставке/удалении/перестановке элементов в середине списка это приводит к неправильному переиспользованию DOM-узлов: состояние `input`, фокус, анимации "прилипают" к неправильным элементам.

**Q5: Что такое Fiber и зачем его ввели в React 16?**

Fiber — переработка внутреннего алгоритма реконсиляции: дерево компонентов представлено как связный список единиц работы (fiber-узлов), обработку которых можно приостанавливать, прерывать и назначать разный приоритет. До Fiber рендер был рекурсивным и синхронным — большое дерево блокировало главный поток целиком без возможности прерваться на более срочную задачу (например, ввод пользователя).

**Q6: В чём разница render-фазы и commit-фазы?**

Render-фаза — вычисление того, что изменилось (вызов функций компонентов, построение нового дерева, diffing); она может быть прервана и перезапущена React'ом, поэтому обязана быть чистой (без побочных эффектов). Commit-фаза — синхронное, непрерываемое применение вычисленных изменений к реальному DOM и вызов эффектов (`useEffect`/`useLayoutEffect`).

**Q7: Почему функция компонента должна быть "чистой"?**

Потому что React может вызвать её несколько раз за один логический рендер (например, в конкурентном режиме, начав и отменив рендер) — сторонние эффекты (мутации внешних переменных, запросы, изменение DOM) при повторных вызовах привели бы к некорректному или недетерминированному поведению. Побочные эффекты должны идти в `useEffect`, вызываемый только после commit.

**Q8: Как смена `key` компонента используется как приём?**

Присвоение компоненту нового `key` заставляет React считать его абсолютно новым элементом: старый компонент размонтируется (state теряется), новый монтируется с нуля. Это официальный способ сбросить внутреннее состояние компонента при смене логической "сущности" (например, смена `userId` для формы редактирования профиля).

**Q9: Что означает "reconciliation" в контексте React?**

Reconciliation (реконсиляция) — процесс сравнения нового Virtual DOM дерева с предыдущим и вычисления минимального набора операций (создать/обновить/удалить/переместить), которые необходимо применить к реальному DOM, чтобы привести его в соответствие с новым состоянием.

**Q10: Является ли Virtual DOM всегда быстрее прямых манипуляций с DOM?**

Нет — для очень небольшого числа точечных изменений прямая манипуляция DOM может быть быстрее (нет накладных расходов на построение дерева и diffing). Ценность Virtual DOM — не в "скорости самой по себе", а в предсказуемости и декларативности: разработчик описывает *что* должно быть на экране, а не *как пошагово* туда прийти, при сохранении разумной производительности за счёт батчинга и минимизации DOM-операций.

## 5. Практическое задание

Реализуй упрощённую функцию `diff(oldTree, newTree)`, которая возвращает список операций для приведения `oldTree` к `newTree`. Дерево — вложенный объект вида `{ type: string; props: Record<string, unknown>; children: Node[] }`. Операции: `{ type: 'REPLACE' }`, `{ type: 'UPDATE_PROPS', changed: string[] }`, `{ type: 'NO_CHANGE' }`. Дочерние узлы сравнивай по индексу (без key — упрощённая версия для понимания принципа).

---

## 6. Решение с инсайтом

```typescript
interface VNode {
  type: string;
  props: Record<string, unknown>;
  children: VNode[];
}

type Patch =
  | { type: 'REPLACE'; node: VNode }
  | { type: 'UPDATE_PROPS'; changed: string[] }
  | { type: 'NO_CHANGE' };

function diffProps(oldProps: Record<string, unknown>, newProps: Record<string, unknown>): string[] {
  const changed: string[] = [];
  const allKeys = new Set([...Object.keys(oldProps), ...Object.keys(newProps)]);
  for (const key of allKeys) {
    if (oldProps[key] !== newProps[key]) changed.push(key); // 🔗 Тема 5: сравнение по ссылке
  }
  return changed;
}

function diff(oldNode: VNode | null, newNode: VNode | null): Patch {
  // Правило 1: узел удалён или добавлен — целиком заменить
  if (!oldNode || !newNode) {
    return newNode ? { type: 'REPLACE', node: newNode } : { type: 'NO_CHANGE' };
  }

  // Правило 1: разный тип — пересоздать поддерево целиком
  if (oldNode.type !== newNode.type) {
    return { type: 'REPLACE', node: newNode };
  }

  // Правило 2: одинаковый тип — сравнить только пропсы
  const changed = diffProps(oldNode.props, newNode.props);
  return changed.length > 0
    ? { type: 'UPDATE_PROPS', changed }
    : { type: 'NO_CHANGE' };
}

function diffChildren(oldChildren: VNode[], newChildren: VNode[]): Patch[] {
  const maxLength = Math.max(oldChildren.length, newChildren.length);
  const patches: Patch[] = [];
  for (let i = 0; i < maxLength; i++) {
    patches.push(diff(oldChildren[i] ?? null, newChildren[i] ?? null));
  }
  return patches;
}

// Тест
const oldTree: VNode = {
  type: 'div',
  props: { className: 'card' },
  children: [{ type: 'span', props: { children: 'A' }, children: [] }],
};

const newTree: VNode = {
  type: 'div',
  props: { className: 'card card--active' }, // изменился className
  children: [{ type: 'span', props: { children: 'B' }, children: [] }], // изменился текст
};

console.log(diff(oldTree, newTree));
// { type: 'UPDATE_PROPS', changed: ['className'] }

console.log(diffChildren(oldTree.children, newTree.children));
// [ { type: 'UPDATE_PROPS', changed: ['children'] } ]
```

> **Инсайт:** Настоящий React-алгоритм устроен сложнее (обрабатывает `key`, списки произвольной длины через двухпроходный алгоритм, приоритеты Fiber), но принцип тот же: минимизировать количество операций с реальным DOM через сравнение дешёвых JS-структур. Понимание этой упрощённой версии объясняет, почему `React.memo` (🔗 Тема 35) и стабильный `key` — не "магия", а прямое управление входными данными для того же самого алгоритма diffing.
