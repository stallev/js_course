## 1. Теория с аналогиями

**Аналогия: контрольный список пилота перед вылетом**

Пилот перед каждым вылетом проходит один и тот же чек-лист — не потому, что забыл, как летать, а потому что рутинная проверка ловит ошибки, которые легко упустить в спешке. Эта тема — такой чек-лист для хуков React: свод правил, разобранных по частям в Темах 29–42, собранный в одном месте для финальной проверки перед тем, как передать код на код-ревью.

**Два формальных правила хуков (Rules of Hooks)**

```
Правило 1: Вызывать хуки только на верхнем уровне
──────────────────────────────────────────────────
✅ Прямо в теле функции-компонента или кастомного хука
❌ Внутри if/for/while
❌ Внутри вложенной обычной функции
❌ После return

Правило 2: Вызывать хуки только из React-функций
──────────────────────────────────────────────────
✅ Из функции-компонента (начинается с большой буквы)
✅ Из кастомного хука (начинается с use)
❌ Из обычной JS-функции
❌ Из обработчика события (внутри, а не как сам хук)
❌ Из класса
```

Оба правила существуют из-за единственной причины, разобранной в Теме 31: React сопоставляет вызовы хуков с "ячейками" состояния по **порядковому индексу вызова** в рамках одного рендера — нарушение правил ломает это сопоставление.

**Разбор эталонного рефакторинга — компонент с несколькими нарушениями**

```typescript
// ❌ Компонент с типичным набором нарушений правил и антипаттернов
function BadUserDashboard({ userId, isAdmin }: { userId: string; isAdmin: boolean }) {
  const [user, setUser] = useState<User | null>(null);

  if (isAdmin) {
    const [adminStats, setAdminStats] = useState(null); // ❌ условный useState (Правило 1)
  }

  useEffect(() => {
    fetch(`/api/users/${userId}`).then(r => r.json()).then(setUser); // ❌ нет отмены (race condition)
  }, []); // ❌ userId отсутствует в зависимостях (stale closure)

  const fullName = user ? `${user.firstName} ${user.lastName}` : ''; // это НЕ антипаттерн — вычисление ок

  const options = { includeAvatar: true }; // ❌ новый объект каждый рендер
  useEffect(() => {
    logPageView(userId, options); // ❌ options как неявная нестабильная зависимость
  }, [userId, options]); // ❌ эффект перезапускается на каждый рендер из-за options

  return <div>{fullName}</div>;
}
```

```typescript
// ✅ Рефакторинг — по одному исправлению на каждое нарушение
function GoodUserDashboard({ userId, isAdmin }: { userId: string; isAdmin: boolean }) {
  const [user, setUser] = useState<User | null>(null);
  const [adminStats, setAdminStats] = useState<AdminStats | null>(null); // хук всегда вызывается

  useEffect(() => {
    let isCancelled = false;
    fetch(`/api/users/${userId}`)
      .then(r => r.json())
      .then(data => { if (!isCancelled) setUser(data); }); // защита от race condition
    return () => { isCancelled = true; };
  }, [userId]); // корректная зависимость — эффект перезапускается при смене userId

  useEffect(() => {
    if (!isAdmin) return; // условие ВНУТРИ эффекта, а не вокруг хука
    fetch(`/api/admin-stats/${userId}`).then(r => r.json()).then(setAdminStats);
  }, [userId, isAdmin]);

  const fullName = user ? `${user.firstName} ${user.lastName}` : ''; // производное значение — ок

  useEffect(() => {
    logPageView(userId, { includeAvatar: true }); // объект создаётся внутри эффекта — не зависимость
  }, [userId]); // стабильная зависимость — только примитив

  return <div>{fullName}</div>;
}
```

**Расширенный ESLint как "автоматический пилот-чек-лист"**

`eslint-plugin-react-hooks` с правилами `rules-of-hooks` и `exhaustive-deps` автоматизирует большую часть этого чек-листа — но не всё: derived state antipattern, избыточная мемоизация, немемоизированный Context value — это архитектурные решения, которые линтер не может обнаружить статически, их выявляют только код-ревью и профилирование.

## 2. Связь со стеком

**React Strict Mode — усилитель для обнаружения нарушений**

```typescript
// app/layout.tsx или корневой рендер
<React.StrictMode>
  <App />
</React.StrictMode>
```

В Strict Mode (и особенно в React 18+ конкурентном режиме) React намеренно **дважды** вызывает функции компонентов и эффекты при разработке — чтобы проявить нарушения чистоты render-фазы (🔗 Тема 30) и отсутствие правильного cleanup в `useEffect` (🔗 Тема 33), которые иначе оставались бы незамеченными до продакшена.

**React Compiler (React 19+) — автоматизация части чек-листа**

Часть антипаттернов, связанных с мемоизацией (`useMemo`/`useCallback`/`React.memo` "на всякий случай" или, наоборот, их отсутствие там, где нужно), в перспективе автоматизируется React Compiler — но правила хуков (Правило 1 и 2) остаются обязательными вручную соблюдаемыми требованиями независимо от версии React.

**TypeScript как дополнительный уровень защиты**

```typescript
// Строгая типизация зависимостей Context (🔗 Тема 37) предотвращает часть runtime-ошибок,
// связанных с забытым Provider, на этапе компиляции, а не в рантайме
function useAuth(): AuthContextValue {
  const ctx = useContext(AuthContext);
  if (ctx === undefined) throw new Error('...'); // компилятор не спасёт от отсутствия Provider,
  return ctx;                                     // но типизация гарантирует форму данных при наличии
}
```

## 3. Лучшие паттерны

**✅ Паттерн 1: Чек-лист код-ревью для PR с хуками**

```
Перед аппрувом PR с новыми/изменёнными хуками, проверить:
1. Все хуки вызываются на верхнем уровне, без условий/циклов вокруг них?
2. exhaustive-deps не подавлен комментариями без явного обоснования?
3. Объекты/массивы/функции в зависимостях — мемоизированы, если это нужно?
4. Нет ли derived state, который можно вычислить без отдельного useState?
5. useMemo/useCallback/React.memo — есть измерение (Profiler), а не "на всякий случай"?
6. useEffect с fetch — есть защита от race condition (AbortController/cancel flag)?
7. Context value — мемоизирован, если это объект?
```

*Почему best practice:* Формализованный чек-лист (аналогично Теме 25 — иерархии проверок) превращает разрозненные знания из тем 29–42 в повторяемый процесс, не зависящий от того, вспомнит ли рецензент конкретное правило в моменте.

**✅ Паттерн 2: "Один компонент — один явный источник правды" на каждый кусок состояния**

```typescript
// ❌ Плохо: totalPrice может храниться и как useState, и вычисляться — двойной источник правды
const [items, setItems] = useState<Item[]>([]);
const [totalPrice, setTotalPrice] = useState(0); // источник правды #2 — риск рассинхронизации

// ✅ Хорошо: totalPrice всегда вычисляется из items — единственный источник правды
const [items, setItems] = useState<Item[]>([]);
const totalPrice = useMemo(() => items.reduce((sum, i) => sum + i.price, 0), [items]);
```

*Почему:* Общий принцип, стягивающий вместе Темы 31 (derived state), 32 (единая логика в reducer), 37 (единый источник — Context, не дублирование в местных state) — весь курс демонстрирует одну идею с разных сторон.

**✅ Паттерн 3: Явное документирование "почему" при отступлении от стандартного правила**

```typescript
// ✅ Осознанное, задокументированное отступление — не молчаливое подавление линтера
useEffect(() => {
  // Намеренно не включаем `onSave` в зависимости: используем useLatest-паттерн (🔗 Тема 36),
  // чтобы избежать пересоздания интервала при каждом изменении обработчика.
  const id = setInterval(() => onSaveRef.current(), 5000);
  return () => clearInterval(id);
}, []); // eslint-disable-line react-hooks/exhaustive-deps -- см. комментарий выше
```

*Почему:* Отступление от правила без объяснения выглядит как забытая зависимость для следующего разработчика (или тебя самого через полгода) — явный комментарий превращает потенциальный баг-репорт в осознанное архитектурное решение.

## 4. Вопросы интервью

**Q1: Сформулируй оба правила хуков и объясни причину каждого.**

Правило 1 — хуки вызываются только на верхнем уровне функции (не в условиях/циклах/после return). Правило 2 — хуки вызываются только из функций-компонентов или кастомных хуков. Причина обоих — React сопоставляет вызовы хуков с состоянием по порядковому индексу вызова в рамках рендера; нарушение любого правила меняет число или контекст вызовов между рендерами, из-за чего индексы "съезжают" и хуки получают данные из чужих ячеек.

**Q2: Почему `use()` из React 19 — исключение из правила хуков?**

`use()` не хранит состояние по порядковому индексу вызова, в отличие от `useState`/`useEffect` — он напрямую читает переданный ресурс (промис или контекст) в момент вызова. Поэтому React официально разрешает вызывать `use()` условно, после раннего `return`, чего нельзя делать с остальными хуками.

**Q3: Как ESLint помогает соблюдать правила хуков и что он не может проверить?**

`eslint-plugin-react-hooks` статически проверяет правило "верхнего уровня" и правило "только из React-функций" (по префиксу `use`/заглавной букве имени функции), а также полноту массива зависимостей (`exhaustive-deps`). Линтер не может обнаружить архитектурные проблемы: derived state antipattern, избыточную или недостаточную мемоизацию, немемоизированный Context value — эти вещи требуют понимания намерения кода.

**Q4: Что общего у большинства антипаттернов, связанных с зависимостями хуков?**

В основе почти всегда лежит referential equality (🔗 Тема 5): объект/массив/функция, создаваемая заново на каждом рендере, всегда "новая" по ссылке для `Object.is`, из-за чего эффекты/мемоизация срабатывают чаще, чем нужно (или не срабатывают, когда изменение реально произошло, но объект остался той же ссылкой при мутации).

**Q5: Как React Strict Mode помогает выявлять нарушения правил работы с хуками до продакшена?**

В режиме разработки Strict Mode намеренно вызывает функции компонентов и эффекты (монтирование/размонтирование/повторное монтирование) дважды подряд — это делает видимыми побочные эффекты, не имеющие правильного cleanup, и нарушения чистоты render-фазы, которые в продакшене (где такого двойного вызова нет) могли бы долго оставаться незамеченными.

**Q6: Почему "derived state antipattern" считается одной из самых частых ошибок начинающих React-разработчиков?**

Интуитивно кажется естественным сохранить любое "интересное" значение в `useState` — но если значение можно вычислить синхронно из существующих props/state, хранение его в отдельном state создаёт второй источник правды, который может разойтись с первым при любом изменении исходных данных, если не предусмотрена ручная синхронизация (что почти всегда забывается в каком-то edge case).

**Q7: Приведи пример, когда правильное с точки зрения линтера использование `exhaustive-deps` всё равно приводит к плохому результату, и как это решить.**

Если функция-колбэк (например, `onSave`) добавлена в зависимости `useEffect` с таймером, эффект будет пересоздавать таймер при каждом изменении `onSave` (даже если это просто новая ссылка без изменения логики) — линтер формально прав, но поведение (постоянный сброс таймера) нежелательно. Решение — паттерн `useLatest`/ref (🔗 Тема 36): держать актуальное значение в `ref`, обновляемом при каждом рендере, а сам эффект оставить с минимальными зависимостями.

**Q8: Что важнее для качества кода с хуками — соблюдение линтера или понимание причины правил?**

Оба важны, но понимание причины первично: линтер защищает от механических ошибок (забытая зависимость, условный хук), но архитектурные решения (когда мемоизировать, как разделить state, когда достаточно `useEffect`, а когда нужен `useLayoutEffect`) требуют понимания *почему* правило существует, а не механического его соблюдения — иначе разработчик либо злоупотребляет `eslint-disable`, либо переусложняет код "на всякий случай".

**Q9: Как связаны между собой темы "Virtual DOM/Fiber" (30) и "правила хуков" (43) — есть ли общая причина обоих механизмов?**

Да — обе темы объясняются одной и той же архитектурной особенностью React: рендер компонента может быть вызван React'ом многократно и в непредсказуемом порядке (Fiber допускает прерывание и повторный запуск render-фазы), поэтому: (1) функция компонента должна быть чистой без побочных эффектов (🔗 Тема 30), и (2) хуки должны вызываться предсказуемо и в одном порядке, чтобы React мог надёжно сопоставить их с состоянием при любом количестве повторных вызовов (🔗 Тема 31, 43).

**Q10: Составь мини-чек-лист из трёх пунктов, которые ты бы проверил первыми при код-ревью незнакомого React-компонента с хуками.**

(1) Все ли хуки вызываются безусловно на верхнем уровне — нет ли `if`/циклов вокруг `useState`/`useEffect`/etc. (2) Есть ли в `useEffect` с сетевыми запросами защита от race condition и корректный cleanup. (3) Нет ли derived state — данных в `useState`, которые можно было бы просто вычислить из уже существующих props/state в теле компонента.

## 6. Решение с инсайтом

**Найденные нарушения:**

1. **Условный `useState` внутри `if (showReviews)`** — нарушение Правила 1 хуков (🔗 Тема 31, Тема 43). При изменении `showReviews` между рендерами число вызовов хуков меняется.
2. **Отсутствие `productId` в зависимостях первого `useEffect`** — stale closure/некорректное поведение при смене `productId` (🔗 Тема 33): компонент не перезагрузит данные при переходе на другой товар.
3. **`filters` — новый объект на каждом рендере**, из-за чего второй `useEffect` (с `logAnalytics`) выполняется на **каждом** рендере, а не только при реальном изменении `productId` (🔗 Тема 33, Тема 35 — referential equality).
4. **`totalRating` — derived state**, хранимый в отдельном `useState` и синхронизируемый вручную через `useEffect`, вместо простого вычисления в теле компонента (🔗 Тема 31 — derived state antipattern).
5. **Отсутствие защиты от race condition** в fetch-запросе — при быстрой смене `productId` устаревший ответ может перезаписать актуальные данные (🔗 Тема 33).

```typescript
function ProductPage({ productId, showReviews }: { productId: string; showReviews: boolean }) {
  const [product, setProduct] = useState<Product | null>(null);
  const [reviews, setReviews] = useState<Review[]>([]); // ✅ хук вызывается всегда (исправление #1)

  useEffect(() => {
    let isCancelled = false; // ✅ защита от race condition (исправление #5)
    fetch(`/api/products/${productId}`)
      .then(r => r.json())
      .then(data => { if (!isCancelled) setProduct(data); });
    return () => { isCancelled = true; };
  }, [productId]); // ✅ корректная зависимость (исправление #2)

  useEffect(() => {
    if (!showReviews) return; // ✅ условие внутри эффекта, а не вокруг хука
    fetch(`/api/products/${productId}/reviews`).then(r => r.json()).then(setReviews);
  }, [productId, showReviews]);

  useEffect(() => {
    // ✅ filters создаётся внутри эффекта — не участвует в сравнении зависимостей (исправление #3)
    logAnalytics(productId, { inStock: true });
  }, [productId]);

  // ✅ derived state — простое вычисление, без отдельного useState/useEffect (исправление #4)
  const totalRating = product?.reviews.reduce((sum, r) => sum + r.rating, 0) ?? 0;

  return (
    <div>
      <p>{product?.name} — рейтинг: {totalRating}</p>
      {showReviews && <ul>{reviews.map(r => <li key={r.id}>{r.text}</li>)}</ul>}
    </div>
  );
}
```

> **Инсайт:** Все пять нарушений в исходном коде — не случайный набор, а типичный "естественный" путь, по которому идёт код без ревью: разработчик добавляет `useState` там, где кажется удобным (условно, для derived data), не задумывается о стабильности ссылок в зависимостях, забывает про race condition, потому что "обычно успевает загрузиться быстро". Именно поэтому чек-лист код-ревью (Паттерн 1) — не формальность, а способ систематически поймать ровно эти пять классов ошибок, независимо от того, насколько опытен автор кода. Это финальная тема курса: все 15 разобранных здесь антипаттернов — прямые следствия механизмов, изученных в Темах 29–42, а не произвольный список "правил ради правил".
